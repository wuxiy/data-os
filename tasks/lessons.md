# 项目教训

## 2026-08-01 数据治理必须作为一等产品界面

- 触发：用户指出数据治理也需要有界面呈现。
- 规则：后续信息架构和原型不得把数据治理等同于 OpenMetadata 后台或单一质量页；必须显式覆盖治理驾驶舱、数据标准、标准映射、数据质量、血缘与影响、问题闭环、数据合同与变更。
- 检查：每次前端范围评审都以上述页面为验收清单，并确保管理者、治理人员和技术人员均有可理解、可操作的视图。

## 2026-08-01 医疗产品配色与责任链必须可信、可溯源

- 触发：用户指出治理驾驶舱左侧高饱和绿渐变质感不足，并追问责任链的数据来源。
- 规则：医疗治理后台不使用高饱和祖母绿、发光或装饰性渐变；采用无渐变深灰松石、暖灰纸面和低饱和灰玉绿，风险色只用于异常语义。
- 规则：责任链不得只展示业务结论；首屏必须显示事件编号、生成/刷新时间，详情必须展示 `issueId → assetId → ruleId → ownerId → ticketId` 关联方式及每个节点的来源系统。
- 检查：视觉验收检查侧栏饱和度和高亮数量；责任链验收检查事件、对象、规则、责任人与工单五类来源能否逐项追溯。

## 2026-08-01 原型 UI 按可发布级别交付

- 触发：用户要求 UI 具备高级感和可发布级别，而非停留在演示稿质感。
- 规则：首版即统一视觉令牌、间距、状态与文案；必须具备响应式、键盘焦点、加载/空/异常反馈、禁用与成功状态，不能出现纯装饰按钮或无反馈点击。
- 检查：交付前运行生产构建，并在桌面工作站视口实测主导航、治理责任链、标准查看、映射保存、质量复检和主索引确认六条路径；逐页检查溢出、对比度和首屏信息层级。

## 2026-08-02 data-ops 实验的结论与资产归属

- 触发：对 data-ops（NiFi 全链路实验项目）的复盘对比；用户明确 data-ops 为一次性实验，不作为交付底座，整体平台建设仍以本项目为主线。
- 结论：data-ops 的 dev 环境基础组件（Doris 集群、Keycloak SSO、部署与 DR 演练脚本）由本项目复用；其实证结论（Doris + dbt 门禁 + SSO 可行，NiFi 服务端过重且院内多源多策略采集支持不足）已回写蓝图第 5.1 节决策记录。
- 规则：中心编排固定 DolphinScheduler、数据库同步固定 SeaTunnel；任何"重新引入 NiFi 服务端"的提议须对照实验结论重新论证。
- 检查：架构评审引用蓝图 §5.1 决策记录；环境搭建优先复用 data-ops dev 资产而非新建。

## 2026-08-01 首版界面只验收桌面端

- 触发：用户明确界面暂时不用考虑移动端使用。
- 规则：首版 UI 以医院信息中心 1280–1920px 桌面工作站为发布目标；已有响应式样式可保留为基础容错，但不再扩展移动端专属交互或把移动适配列为验收项。
- 检查：后续设计评审、概念对照和交付截图以 1440×900 为基准，并补做 1280px 最小桌面宽度溢出检查。

## 2026-08-04 专业入口必须是真实深链，配置编辑器默认可见

- 触发：用户反馈数据资产“技术视图”和智能问数“专业工作区”点击后无法打开，并指出采集配置 JSON 默认没有展开。
- 规则：所有“打开技术视图/专业工作区”按钮必须使用可访问的真实 `target="_blank"` 深链，路由、SPA 回退和导航激活状态三者同时注册；不能只弹提示文案替代打开动作。
- 规则：任务配置 JSON 在新建任务和编辑任务抽屉中默认展开，且必须明确显示“默认展开 · 可编辑”，避免把关键配置藏在二次点击之后。
- 检查：每次门户交付运行 `node prototype/qa/portal-interactions-smoke.mjs`，同时检查旧提交应失败、当前提交应通过；生产构建后再验收深链 HTTP 回退。

## 2026-08-04 本地浏览器验证优先于“环境不可用”结论

- 触发：用户指出此前可以在本地进行浏览器真实验证，要求补做截图、DOM 和交互回归。
- 规则：先连接可用的浏览器自动化能力；本地静态预览验证页面与深链，若页面依赖开发环境 API，则通过安全的本地端口转发接入真实控制面，再验证真实数据状态。
- 检查：桌面 1440×900 视口至少覆盖页面身份、非空渲染、控制台错误、截图和一条真实交互；结束前复位临时视口并清理标签页。

## 2026-08-05 治理动作必须区分“请求登记”和“规则执行结果”

- 触发：质量闭环接入真实问题 API 时，复检接口先完成状态与事件持久化；代码审查指出不能把 `RECHECKING` 当作质量规则已经执行完成。
- 规则：门户必须显示动作的真实语义；“开始复检”只代表请求已登记时，应在事件、文案和交付复盘中明确等待执行器异步回写结果，不能伪造通过/失败证据。对 `RECHECKING` 状态要前后端同时防重复提交。
- 检查：契约测试覆盖关闭问题和复检中问题的冲突边界；页面详情请求失败必须在当前主区域展示可见错误，不能只写入未渲染的侧栏状态。

## 2026-08-05 远程门户静态包更新后必须重建挂载容器

- 触发：开发机通过 rsync 更新了 Nginx bind mount 目录，宿主机 index 已是新 hash，但容器内仍读取旧 inode，浏览器因此误判执行批次 UI 未发布。
- 规则：门户静态包更新后，除了校验宿主机文件，还必须 `docker exec portal grep` 校验容器内 index/asset hash；若 bind mount 使用只读目录且容器仍保留旧 inode，执行 `docker compose up -d --force-recreate portal`，不能只重载控制面。
- 检查：浏览器验证前同时比对 `curl 入口 index`、`document.scripts[].src` 和目标 bundle 文本；确认与本地 `prototype/dist` hash 一致后再进行交互验收。

## 2026-08-05 外部投递工作流必须可恢复且可抢占

- 触发：第六轮代码复检发现质量复检提交中间态未被后台恢复扫描，通知投递也没有数据库原子 claim；同时页面在请求成功时没有区分“已登记”和“已投递”。
- 规则：所有“先落库、再调用外部执行器/通道”的流程都必须扫描中间态，短暂不可用保留待重试，通知投递用租约/条件更新抢占并在状态完成时校验 worker；前端按返回的执行批次状态提示真实语义。
- 检查：测试覆盖重启后的 `SUBMITTING` 恢复、通知并发 claim、Webhook 成功/失败退避，以及 `RECHECKING` 期间禁止改写工作流。

## 2026-08-05 幂等键必须覆盖“事件 + 通知”整体

- 触发：复审发现主动提醒先写事件、再按幂等键入队时，同一 `Idempotency-Key` 的并发请求虽然只保留一条通知，仍可能留下两条事件。
- 规则：幂等资源必须先抢占唯一键，再由抢占成功的一方写事件；返回已有记录时不能追加副作用。外部提交也必须把成功、失败和退避更新绑定到当前 worker 租约。
- 检查：并发提醒测试同时断言事件数和通知数均为 1；最终远程验收重复发送同一键后查询结果保持一致。

## 2026-08-05 mock 必须显式开启，API 失败不能静默回退

- 触发：继续推进可用时发现治理驾驶舱在控制面请求失败后仍显示本地问题列表，管理/资产/分析/问数等页面也会直接渲染静态样例，容易让甲方把原型数据当成真实结果。
- 规则：生产构建默认真实模式；静态样例必须经过 `VITE_DATAOS_DEMO_MODE=true` 和页面边界组件；控制面失败只展示可见不可用/待接入状态，不使用业务 mock 补位。
- 规则：`DEMO` 质量执行器必须由后端显式开关启用，生产默认关闭；运行状态接口只报告配置状态和告警，不暴露 URL 或密钥。
- 检查：每次门户交付运行 `npm run qa:mock`，并在真实模式、显式演示模式各做一次浏览器验证；治理驾驶舱不得出现静态责任链、趋势和 fallback 问题。

## 2026-08-05 mock 边界必须在后端再次校验并默认 fail-closed

- 触发：代码审查发现真实模式前端虽然隐藏 FakeSource，但历史演示任务仍可能通过旧入口启动；同时仅依赖前端环境变量会让生产配置存在绕过风险。
- 规则：演示模板和 FakeSource 配置在控制面保存/启动路径必须按运行环境再次校验；`DATAOS_RUNTIME_ENV` 未显式标记开发时按 production 处理，环境值和执行器名称先 trim 再比较。
- 检查：覆盖生产环境保存、历史任务启动、空格绕过和开发环境允许演示模板的单元测试；文档明确开发 Compose 必须显式设置 development。

## 2026-08-06 OIDC 已存在时不引入第二套鉴权

- 触发：发布级 Gate 0 讨论中确认开发环境已有 Keycloak/OIDC，用户询问是否还需要 Sa-Token。
- 规则：当 OIDC 已作为统一身份源时，Spring Boot 控制面只实现 Resource Server JWT 校验、角色映射、租户声明和审计；不再叠加本地会话或 Sa-Token Token，避免双重登录、权限漂移和撤销链路分裂。
- 检查：生产启动必须要求 OIDC issuer、audience 和受信租户声明；DISABLED 仅允许隔离开发/测试 profile，不能作为生产回退路径。

## 2026-08-07 远程验证先做只读连通性，再区分服务状态与凭据状态

- 触发：用户要求连接开发环境验证；SSH 端口可达但提供的登录凭据被拒绝。
- 规则：先用 HTTP/HTTPS 健康检查确认目标服务是否可达，再尝试 SSH；认证失败时不得继续猜测口令或声称已部署。远程现有 DEMO 状态、未监听的调度器端口和本地未部署的最新制品必须分别记录。
- 检查：验证记录必须同时包含健康响应、调度器端口、凭据阻断原因和未执行的写入动作；获得新凭据后再做远程 Compose/数据库变更。

## 2026-08-08 公钥恢复后远程变更仍必须先留回滚点

- 触发：用户补充开发机已配置 SSH 公钥，允许从只读盘点进入远程部署。
- 规则：密钥可用只解决认证阻断，不等于可以跳过备份；先保存配置、制品和容器 inspect，再执行新服务部署。镜像加速器异常时优先逐镜像导入，不重启共享 Docker 守护进程；重建被 Nginx 代理的上游容器后必须重启/重载代理刷新容器 DNS。
- 检查：部署记录要同时写明回滚目录、健康响应、token 是否仅落在秘密文件、现有业务容器是否保持运行，以及未完成的真实工作流验收边界。

## 2026-08-08 临床连接器没有真实端点时不得伪造业务验收

- 触发：将隔离 Shell 验收替换为 LIS、EMR、手术系统工作流时，开发机只有平台组件，没有院内真实主机、只读账号和脱敏样本。
- 规则：先交付版本化连接器合同、凭据引用解析和配置阻断；只有拿到真实端点、账号、目标表和样本后，才创建并运行业务任务。健康检查、模板列表和单元测试不能被描述为真实临床数据已接入。
- 规则：调度器历史 Shell 工作流必须归档，生产和开发都不依赖 default tenant 回退；DolphinScheduler 服务账号、工作流绑定和 data-os OIDC tenant/institution 必须使用命名范围。
- 检查：验收报告同时列出已验证的合同/运行时边界、远端命名租户与回退开关，以及等待甲方补齐的端点/凭据/样本清单。

## 2026-08-08 院方环境默认按离线制品交付

- 触发：用户明确院方生产环境通常位于隔离内网，无法从互联网直接推送或拉取镜像，大概率只能在外网构建后通过受控介质拷贝部署。
- 规则：镜像仓库推送不得作为生产交付的必需前提；发布主路径必须生成可独立验真的离线镜像包、SHA-256、SBOM、许可证清单、版本清单和导入脚本。院方内网仓库只作为离线导入后的可选分发层。
- 检查：在完全无互联网、无外部 Registry 的环境中执行校验、`docker load`、Compose 启动和回滚演练；文档不得要求部署机在线下载连接器、基础镜像或扫描工具。

## 2026-08-08 SeaTunnel 离线镜像验证必须以官方 tar 实际布局为准

- 触发：首次构建时把 `plugin-mapping.properties` 误判为 `config/plugin-mapping.properties`，官方 2.3.13 tar 实际路径是 `connectors/plugin-mapping.properties`；SHA-512 校验通过后构建在布局检查处失败。
- 规则：任何发布包解压后的目录断言必须来自目标版本 tar 的实际清单，并在构建机执行一次离线构建；不能只依据旧 Dockerfile 或文档猜路径。
- 检查：构建脚本/ Dockerfile 失败时先保留精确错误，修正路径后重新跑完整 `OFFLINE_BUILD=true` 构建、连接器/驱动存在性和 `/overview` 健康检查。

## 2026-08-08 Doris 连接器的隐式 JDBC 依赖必须纳入默认 profile

- 触发：JDBC→Doris 冒烟第一次提交时，Doris catalog 初始化报 `No suitable driver`
  （连接 `jdbc:mysql://.../information_schema`），仅放入 PostgreSQL 驱动并不足以让
  Doris sink 工作。
- 规则：固定 Doris sink 的镜像 profile 必须同时包含 MySQL Connector/J；驱动清单要
  记录其版本、SHA-256 和许可证边界，不能等到真实目标库才发现依赖缺失。
- 检查：在目标 FE 不可达的环境仍应看到错误进入“Failed to connect”而不是“No suitable
  driver”；随后用同一镜像完成 JDBC→Console 合成作业，确认 SeaTunnel 启动与 JDBC
  source 没有被驱动修复破坏。

## 2026-08-09 明文 Python HTTP Runtime 必须显式固定 HTTP/1.1

- 触发：控制面调用质量 Runtime 时，JDK `HttpClient` 默认尝试 h2c 升级；Uvicorn/h11 明文端口记录 `Invalid HTTP request`，控制面把请求误判为 HTTP 400/422，质量复检进入 `SUBMIT_FAILED`。
- 规则：凡是通过 `http://` 调用 Uvicorn/轻量 Python 服务，JDK 客户端必须显式设置 `HttpClient.Version.HTTP_1_1`；不能只依赖默认协商，也不能把一次直连 `curl` 成功当成 Java 客户端成功。
- 检查：部署后同时查看 Runtime access log 的 `POST /api/v1/quality/runs`、控制面执行批次的 `externalId/status` 和 h2c 警告；最终要验证 `HTTP → dbt → 回写 → 自动关闭`，再记录通知回执和审计表清理。

## 2026-08-11 四项可交付路线必须形成真实闭环

- 触发：发布级审查发现生产质量问题只有演示初始化来源，采集水位停留在文档，私网 allowlist 与开发凭据回退边界混淆，且质量运行器的失败证据清理与租约恢复没有完整门禁。
- 规则：生产质量事实必须通过受保护的 finding ingress，以来源系统、finding key 和执行批次幂等落库；采集水位必须写入运行记录，仅在 sink 成功后推进；`allowPrivateNetworks` 不等于 local mode，院内私网端点仍必须使用 credentialRef；中间态必须可恢复，UNKNOWN 只允许人工同步；没有真实端点不得宣称临床已接入。
- 检查：每轮交付至少运行 Java 全量测试、quality-runner pytest（包含 pytest-asyncio）、回放源真实 HTTP smoke、生产/开发 Compose config 和 `git diff --check`，并在复盘中列出真实院端点、账号、目标表和样本的未完成交接项。

## 2026-08-11 RustFS 开发部署必须验证 SSE-S3 写入与 SELinux 挂载

- 触发：RustFS 健康检查和桶初始化均成功，但质量运行器首次写入摘要时被 RustFS 拒绝，原因是 SSE-S3 未配置 32 字节 Base64 主密钥；同时新门户静态目录在启用 SELinux 的开发服务器上因 bind mount 标签不匹配返回 403。
- 规则：对象存储验收不能只检查 `/health` 和 `list_buckets`，必须实际 `PutObject`/读取一条脱敏制品；Compose 必须显式注入 SSE-S3 主密钥且只保存在 `0600` 的远程 Secret 文件。Linux/SELinux 开发机的只读静态 bind mount 使用 `:Z` 并在容器内检查入口文件。
- 检查：部署后运行一条真实合成质量规则，确认 `SUCCEEDED`、`artifactUri=s3://...` 和桶内对象存在；执行门户 `/`、`/healthz`、JS bundle 的 HTTP 200 检查，并记录回滚快照和无密钥验收证据。

## 2026-08-11 Doris 失败表名称必须纳入租户命名空间长度预算

- 触发：质量运行器将租户哈希与 dbt selector 拼接为失败表名时超过 Doris 64 字符限制，任务虽能启动却无法落表/回写制品。
- 规则：设计 dbt 失败表命名时先按目标库标识符上限预算租户命名空间和 selector 长度；当前内置规则保留 18 位哈希（72 位熵），为最长 selector 留出空间，并在远程合成规则上真实执行验证。
- 检查：至少覆盖最长已注册 selector 的 Doris `dbt test --store-failures`，同时确认失败表清理逻辑使用相同命名空间，不能只做 Python 单元测试。
