## 三、关键发现（影响 G16b 设计）

1. **患者身份域存在且活跃**（计划制定时未知）：`PATIENT` 表为 C 端注册/实名认证路径的患者主档（NAME/PHONE/CARD_NUMBER/GENDER/BIRTHDAY），`PATIENT_CARD` 为就诊卡映射（含亲情账号 RELATIONSHIP），`PATIENT_EP_RECORD` 提供患者↔处方关联键——T5b 第二身份流从「次候选（EP_FLOW）」升级为「最强候选（患者域）」。
2. **敏感列硬约束**：`PATIENT` 含 `PASSWORD`、`CREDENTIALS`、`WECHAT_OPEN_ID` 三列，G16b 采集作业必须显式列清单排除，禁止 `SELECT *`；该项写入计划 §4.1 执行约束。
3. **行数波动**：`EP_MZ_CFZB` 当前 11,420 行（历史 Gate 时点 11,373 / G13 时点 11,442），测试库有增删；G16b 增量对账以源库现值为准。
4. **源库活跃度**：多表业务时间上界为盘点当日（2026-09-02），增量采集有持续输入保障。

## 四、与方案的偏差（如实记录）

1. **工期**：计划预估 G16a 约 1 周（3–5 人日）；实际在本对话内一次完成（盘点程序 + 分析 + 文档约数小时）。原因是盘点面为纯只读元数据查询、表规模小（总计 ~306 万行）、无等待类工作；提前完成不改变 G16b 边界。
2. **凭据获取方式**：EP 口令从开发机 `.env` 经 SSH 读入环境变量、仅存内存，未在本机落盘、未进 Git/日志（与既有安全口径一致）。
