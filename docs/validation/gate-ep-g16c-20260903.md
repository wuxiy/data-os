## 三、本批关键事实

1. **源表 ORDER 是 SQL 保留字**：Doris 侧交易域 6 表统一 `ep_` 前缀（ep_order / ep_order_item / ep_order_flow / ep_order_trade / ep_order_relationship / ep_order_after_sale），机构维度保持原名小写；DM 源查询对 ORDER 加双引号。命名偏差已写进 DDL 头注释。
2. **交易域关联键是业务串 ORDER_SN**（非 ID 外键）：ORDER.SN 唯一（6,691 全唯一），四张子表 ORDER_SN→SN 全部 0 孤儿；EP_ID→ep_mz_cfzb.ID、PATIENT_ID→patient.ID 亦 0 孤儿——七条 FK 边全部在册且全绿。
3. **主表滞后是复发性形态**（G16b 已见）：源库持续新增处方，子表当天入库引用新主表行，FK 目标快照滞后即失败。本批根治：新增「电子处方主表增量」作业（水位 UPDATE_TIME，UNIQUE KEY UPSERT），FK 目标可随增量保鲜；本批验收中以一次全量刷新闭环。
4. **rr 降维工具的收敛上限**：dbt 1.10 每条 result 带 `batch_results`，OM 1.5.11 解析器拒绝；原迭代式剥离每轮 3 键 × 15 轮，测试数过 ~45 即翻车（本批 60 条实测）。补丁：统一前置剥离 batch_results（deploy/scripts/dbt-compat-rr-downgrade.py），迭代循环只兜零星键。
5. **OM dbt 资产化面实效复查（重要更正）**：OM 实体面查询确认 **DataModel 全局 0、TestCase 0**——G7 的 dbt 资产化（TestCase+DataModel 挂靠）在 OM 1.5.11 上当前不落任何实体（工作流「Processed 29 / Success 100%」是内部处理计数）。G16b 报告中「dbt DataModel 29 条落地」表述有误，已更正。TestCase 零登记本为 P3 已知；DataModel 面同批确认同样未落库，**统一归口 P3（OM 升级窗口一并验证恢复）**。G6 表结构资产面不受影响（三库零差异）。
6. 摄取脚本内置 compat 测试跑出 5 个 ERROR，全部为合成验收表（quality_acceptance_*）在 compat 容器下的既有行为，与本批 55 条真实表测试无关（后者全 PASS）。
