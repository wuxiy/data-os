## 二、批次划分（按依赖与价值排序）

### H1：OM 升级窗口（P3）——最高优先，独立可先行

- **内容**：OM 1.5.11 → ≥1.6（全新卷重建为首选：dev 元数据可脚本重放，G6/G7 摄取脚本幂等）；升压前置 Keycloak/Superset 联动面检查；升级后验证三个受阻面恢复（G7 TestCase、G11 term 回写、dbt DataModel/TestCase）+ G6 表结构面零回归。
- **工作量**：3–5 人日（含数据卷策略决策与重放验证）。
- **风险**：OM 1.6 API 变更可能波及 om-ingest 系脚本与 BFF 列打标（G9 记忆：OM 列打标索引+tags 依赖 1.5 行为）——升级验证清单须含 G9 面回访。
- **为何最先**：三个受阻面中 dbt 资产化已让质量测试资产化名存实亡；且越晚升级，卷迁移的存量越大。

### H2：认证收口（S8 + S4 余项 + S7 truststore 余项 + S3）

- **内容**：data-api `/internal/**` 切 ENFORCED（Keycloak client `dataos-data-api`，compose 键位已预留）；guest-token 按用户维度重设计；JWKS 自签→truststore；Superset CSP 显式 frame-ancestors（依赖生产域名定稿——若域名未定则本项继续延后，不阻塞批内其他项）。
- **工作量**：4–6 人日。
- **依赖**：Keycloak 现状即可，无 H1 依赖。

### H3：Data API 生产化（P7 + P8 核心）

- **内容**：P7 异步导出至对象存储（复用 RustFS artifacts 模式：导出任务 → 上传 → 下载 URL → 生命周期清理）；P8 取核心子集（网关级限流/熔断 + 审计回写失败持久化缓冲）；调用方自助门户与合同变更通知继续延后（真实调用方出现前无验收对象）。
- **工作量**：5–8 人日。
- **依据**：Data API 已有 8 个数据集（G13×3 + G16×5），maxRows 截断已是可感知限制。

### H4：编排与运维收口（P2 + P1 + S1 残留 + P4 + P5 + S6 余项）

- **内容**：OM/dbt/血缘摄取脚本接进控制面外部运行状态机（适配非新建）；MiNiFi 三收敛（部署脚本化/黑盒监控/版本冻结）；RustFS AK/SK 轮换（2 作业停机窗口）；`doris-medical` 遗留处置；断网缓冲大容量与桶生命周期策略；源库凭据全账号面复查。
- **工作量**：6–9 人日。
- **依赖**：P2 部分依赖 H1（升级后摄取行为先稳定再编排）。

### H5：测试工程（T1 + T3 + T4）

- **内容**：全链路压测基线（SeaTunnel/Doris/BFF）；跨服务契约测试自动化（替代 gate 手工验收）；故障注入回归套件（断网/重启/503 面/幂等重放——G16b 的 SUBMIT_FAILED 风暴与 UNKNOWN 对账路径是现成用例素材）。
- **工作量**：8–12 人日。
- **依赖**：建议最后（对稳定面测试；T3 可与 H1-H4 并行增量做）。
