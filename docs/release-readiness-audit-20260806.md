## 1. 执行结论

data-os 已经具备一套界面完成度较高、边界表达较诚实的医疗数据平台演示产品，并落地了“数据源检查 → 采集任务 → SeaTunnel 执行 → 治理问题 → 质量复检 → 结果回写 → SLA/通知队列”的第一条真实控制面纵切。但它目前仍不具备医院生产发布条件，也不应标记为 1.0 或对外宣称“完整数据平台已交付”。

当前建议定位：

- 可以发布为 `0.2 Pilot Preview`，用于售前演示、方案确认和受控开发联调。
- 补齐本文 P0 后，可进入单院受限试点；试点范围应明确限制在 JDBC/HTTP/SFTP 批量或增量采集、质量闭环和资产检索，不承诺区域多租户、完整主索引、智能问数生产服务。
- 完成 P0、P1 和发布验收门禁后，才适合定义为单院生产版。
- 区域平台还需额外完成组织隔离、跨机构标准、区域 MPI、容量与容灾验证，不能直接复用单院试点结论。

本次成熟度评分是用于排定缺口优先级的工程估算，不是等保、密评、医疗行业合规或第三方测评结论：

## 4. P0：阻断试点或生产发布的问题

### P0-01 无身份认证、权限控制和可信审计

控制面依赖中没有 Spring Security/OIDC，业务 API 可匿名读取和修改。远程开发环境匿名访问治理摘要成功，治理工作流、复检、提醒、手工 SLA 扫描和通知投递均存在公开写入口。

发布前至少需要：

- Keycloak/OIDC 登录和令牌校验；门户和控制面统一会话。
- 平台管理员、机构管理员、数据开发、数据治理、数据负责人、审计员、只读用户等角色。
- 菜单、按钮、接口、机构、主题域、数据资产和字段级授权。
- 登录、查询、导出、配置修改、规则执行、MPI 合并/拆分和权限变更审计。
- 审计记录防篡改、保留期和可检索导出。

代码证据：`services/control-plane/pom.xml:24` 起只有 Web、JDBC、Validation、Actuator 等依赖；`GovernanceController.java:34-108` 直接暴露查询与写操作。

### P0-02 租户和机构隔离由调用方传参，区域场景不可用

当前 tenant/institution 可从 query/body 传入并默认 `default/demo-hospital`，不是从登录身份解析的可信上下文；部分按 ID 查询和状态操作未证明带租户约束。调用方可能横向访问或修改其他机构数据。

发布前需要：统一 `TenantContext`、令牌声明映射、所有表的 tenant/institution 强制列、仓储查询强制过滤、唯一键含租户、跨租户负向测试，以及管理员跨机构操作的显式授权和审计。

### P0-03 数据源检查存在 SSRF 与内网探测风险

HTTP 检查适配器直接请求用户提供的 URL，JDBC 检查直接使用用户提供的 JDBC URL 和密码。在 API 无鉴权的情况下，调用者可以借控制面访问内网服务、云元数据地址或数据库端口。

发布前需要：来源类型白名单、协议白名单、DNS/IP 解析校验、阻止 loopback/link-local/metadata/未授权内网段、出口代理或 egress policy、请求超时和响应大小限制、URL 重定向复检，以及按机构授权的网络策略。

代码证据：`HttpSourceCheckAdapter.java:26-33`；`JdbcSourceCheckAdapter.java:19-27`。

### P0-04 缺少凭据服务，真实采集不能安全闭环

任务配置明确禁止持久化 password/secret/token，但系统没有凭据引用模型、密钥存储、解析器和轮换机制。连通性检查虽然接收一次性明文密码，却不能形成可调度任务的安全凭据引用。因此需要认证的 JDBC、HTTP、SFTP 等生产任务实际上尚未完整落地。

发布前需要：`credentialRef` 契约、Vault/Kubernetes Secret 或受控数据库加密方案、仅控制面/执行器可解密、日志脱敏、轮换、失效、使用审计、导出时剔除秘密，以及 SeaTunnel 提交时的短时注入。

### P0-05 没有生产部署基线

仓库只有开发 Compose。当前门户仅 HTTP，无 TLS 和安全响应头；镜像默认 root 用户、可写根文件系统、无 CPU/内存限制；镜像标签未固定 digest。data-os 控制面复用 Keycloak 的 PostgreSQL 数据库和 `keycloak` 账号，不符合生产隔离和最小权限。

发布前需要：

- 单机交付可选的 hardened Compose，以及区域/高可用形态的 K3s/Helm 清单。
- 独立数据库、独立账号、最小权限和连接池容量设置。
- TLS、受信证书、CSP/HSTS/X-Content-Type-Options/Frame-Options 等响应头。
- 非 root、只读根文件系统、资源 request/limit、健康探针、优雅停机和日志卷策略。
- 不可变镜像、版本清单、离线包、校验值和配置模板。

配置证据：`deploy/dev/docker-compose.yml:8` 复用 Keycloak DB；`:47` 暴露 HTTP 门户；`services/control-plane/Dockerfile:1` 起未设置 `USER`；Nginx 配置未设置安全响应头。

### P0-06 数据库没有版本化迁移、备份恢复和灾备验证

控制面通过 `spring.sql.init.mode=always` 重复执行单一 `schema.sql`，没有 Flyway/Liquibase 版本、迁移历史、向前兼容窗口和失败回滚。仓库也没有数据库/元数据/配置备份脚本、恢复演练、RPO/RTO 或跨节点恢复证据。

发布前需要：Flyway/Liquibase 基线、每版本迁移、扩展再收缩策略、升级前备份、恢复校验、回滚或前滚手册，以及至少一次空环境恢复和跨版本升级演练。

代码证据：`services/control-plane/src/main/resources/application.yml:16`；`schema.sql:1`。

### P0-07 核心业务能力仍以原型代替真实服务

“完整医疗数据平台”的关键承诺包括资产、标准、映射、主索引/主数据和数据服务。当前这些模块未形成控制面 API 和持久化服务；管理驾驶舱、分析和问数也主要是静态页面。在真实生产构建中，页面会明确显示“待接入真实服务”。

若希望尽快试点，可通过合同和版本范围把这些能力排除在首期外；若对外宣称完整平台，则必须在发布前实现，不能只用 OpenMetadata、Superset、DB-GPT 的独立登录页面替代 data-os 产品能力。

### P0-08 真实数据执行链尚未经过生产级端到端验收

开发环境质量执行器为显式 DEMO 适配器，通知 Webhook 未配置。尚无“真实院内源 → SeaTunnel → 目标库/湖仓 → dbt/质量执行器 → OpenMetadata → 门户证据”的完整验收，也没有 CDC 位点、断网续传、重复数据、故障重启和大数据量验证。

发布前至少选择一套标准交付栈完成真实闭环，例如 PostgreSQL/Oracle/MySQL 源、SeaTunnel、Doris/PostgreSQL ODS、dbt/规则执行器、OpenMetadata 和企业微信/邮件/Webhook 通知，并沉淀可重复的验收数据集和报告。

## 5. P1：试点稳定运行前应补齐

1. **运行恢复**：SeaTunnel 运行同步目前使用进程内 `inFlight`；多副本可能重复轮询。`UNKNOWN` 运行可能长期占用活动状态。需数据库租约、陈旧运行回收、取消/终止、死信和人工修复入口。
2. **前置机采集**：实现轻量 Agent/Minifi 替代方案、出站连接、断点续传、本地缓冲、带宽限速、远程配置签名、离线升级和运行诊断。
3. **连接器产品化**：Oracle、MySQL、SQL Server、PostgreSQL、FTP/SFTP、文件、HTTP、FHIR/HL7 模板；字段提示、连接测试、增量键、时间窗口和错误解释。
4. **分页与容量边界**：来源、任务、运行等列表需服务端分页、排序和过滤；限制名称、JSON、样本证据、上传文件和响应大小，避免无界读取。
5. **统一错误契约**：数据库约束、上游超时、执行器错误不能以不透明 500 暴露；增加错误码、traceId、可操作建议和敏感信息清理。
6. **全局筛选真实联动**：当前机构、主题域、时间选择只提示，不影响 API 或图表；需统一查询上下文、URL 状态和导出条件。
7. **真实通知通道**：至少接入一种医院可用通道并验证送达、签名、重试、下游幂等、限流和失败告警。
8. **可观测性**：结构化日志、traceId、业务指标、Prometheus、Grafana、告警规则、运行日志检索、质量/通知死信看板和组件健康总览。
9. **API 契约**：OpenAPI 文档、版本策略、幂等要求、兼容窗口、错误字典、Webhook 签名和客户端示例。
10. **CI/CD**：提交触发后端测试、前端构建、lint/typecheck、镜像构建、SBOM、依赖/CVE/secret 扫描、集成测试和制品签名；环境晋级需审批与证据。
11. **测试体系**：前端单元/组件/E2E，PostgreSQL/Testcontainers，真实 SeaTunnel 持续集成，性能、长稳、故障注入、并发、多租户越权、安全、升级和恢复测试。
12. **供应链与许可证**：生成 Maven/npm/镜像 SBOM，第三方许可证清单，固定基础镜像 digest，扫描高危漏洞，建立修复 SLA。
13. **资源与容量模型**：给出小型单院、中型单院、区域三档 CPU/内存/磁盘/网络估算，验证并发任务数、日增量、元数据量和保留期。
14. **交付证据**：安装手册、网络端口表、配置清单、巡检表、备份恢复手册、升级回滚、故障码、验收用例和交接培训材料。

## 7. 工程与运行风险明细

### 7.1 API 与数据模型

- 控制面约 22 个 HTTP 端点，覆盖范围集中在 source/job/run/governance/quality/notification/runtime，不等于完整平台服务面。
- 多数列表无服务端分页；长期运行后会拖慢接口与门户。
- 部分按 ID 操作缺少可证明的 tenant 约束。
- 多个文本和 JSON 字段缺少应用层最大长度校验，数据库异常可能变为 500。
- 没有正式 OpenAPI、客户端兼容策略和废弃策略。

### 7.2 任务执行与一致性

- 任务/复检/通知已有幂等或数据库租约设计，是正确基础。
- SeaTunnel 运行同步仍依赖单进程内存状态，尚未证明水平扩展安全。
- 外部 Webhook 的极端崩溃窗口依赖下游按 `idempotencyKey` 去重，必须写入接入契约并实测。
- 缺少作业取消、强制终止、卡死检测、死信重放和跨版本兼容验证。

### 7.3 前端产品行为

- 桌面端视觉、层级、空态和错误反馈已达到良好原型水准。
- 8 个主要静态产品页面通过 `DemoDataBoundary` 管理真实/演示边界；边界表达清晰。
- 真实模式下首页、资产、标准、映射、MPI、分析和智能问数没有真实数据服务。
- “数据服务、运营中心、交付中心、系统设置”等入口无产品路由，仅显示提示。
- “血缘与影响、问题闭环、数据合同”等治理页签没有路由。
- 全局医院/主题域/时间筛选不改变数据请求。

### 7.4 部署与供应链

- 只有开发 Compose；SeaTunnel 是单 master/worker 开发形态。
- 容器未配置 CPU/内存限制、非 root 和只读根文件系统。
- 无 Prometheus/Grafana、发布流水线、离线制品、SBOM、签名和漏洞门禁。

- npm 使用官方 registry 审计为 0 个已知漏洞；Maven 和容器尚未完成等价漏洞审计。

### 7.5 医疗数据与合规

即使早期方案允许暂缓安全，生产发布也不能继续暂缓。尚缺：

- PHI/PII 字段分级、默认脱敏和最小可见。
- 查询、预览、下载、导出、问数和 MPI 裁决的审计。
- 数据保留、归档、删除、匿名化和项目退出销毁流程。
- 样本证据的脱敏、限量和访问授权。
- 数据使用目的、授权范围和跨机构共享审批。
- 管理员双人复核、高危操作二次确认和应急账号流程。

这些要求最终需由客户等级保护、密码应用、医院制度和当地监管要求共同确定；本文只给出产品工程基线。

## 9. 分阶段实施计划

以下工期按 4–6 人稳定团队、基础环境和客户接口人及时到位估算；2–3 人团队通常需要 20–30 周。工期不是承诺，应在真实数据源和医院网络勘察后校准。

### Gate 0：发布基础线，2–3 周

目标：先把“任何人都能调用的开发服务”变成可受控部署的软件。

- Keycloak/OIDC、RBAC、可信租户上下文和关键操作审计。
- SSRF 防护、凭据引用服务、日志与错误脱敏。
- Flyway/Liquibase、独立数据库账号、生产配置分层。
- TLS、安全响应头、非 root 镜像、资源限制、不可变版本。
- CI、SBOM、依赖/Secret 扫描、基础 Prometheus 指标和告警。

退出标准：未登录访问业务 API 为 401；越权用例通过；秘密不落库不入日志；空库可迁移启动；生产配置下 DEMO/FakeSource 启动失败；安装和回滚可重复。

### Gate 1：单院受限试点核心，4–6 周

目标：完成至少一条医院真实数据端到端链路。

- JDBC/HTTP/SFTP 连接器模板、凭据注入、调度、增量和失败恢复。
- 前置机 Agent 最小闭环：出站连接、本地缓冲、断点续传和远程诊断。
- 目标存储与 dbt/真实质量执行器，规则、批次、样本和趋势。
- OpenMetadata 资产目录、元数据采集、搜索和最小血缘。
- 真实通知通道、作业取消/卡死回收、分页与错误契约。
- 前端 E2E、Postgres/SeaTunnel 集成测试和标准验收数据集。

退出标准：真实院内测试源连续运行 7 天；断网/重启不丢位点且不产生不可控重复；质量结果和资产元数据可追溯；通知可送达；所有失败有可恢复路径。

### Gate 2：医疗治理产品，5–8 周

目标：从“采集与质量工具”扩展为医疗数据治理平台。

- 数据标准、值域、映射、版本、审批和落标检测。
- 患者 MPI 最小产品：候选、裁决、合并、拆分、黄金记录和审计。
- 主数据模型、发布订阅与回执。
- HL7/FHIR 接入模板和医院常见主题域标准包。
- 数据服务目录与申请授权；Superset 安全嵌入。
- 运营中心与交付中心的最小真实功能。

退出标准：用脱敏医院样本完成标准映射、MPI 人工裁决、资产血缘、服务授权和分析访问全链验收。

### Gate 3：生产发布加固，3–4 周

目标：形成可升级、可恢复、可运维、可签收的软件制品。

- 容量、并发、性能、72 小时长稳、故障注入和多副本测试。
- 备份恢复、RPO/RTO、升级/前滚/回滚演练。
- 安全测试、依赖与镜像漏洞收敛、许可证核查。
- 监控看板、告警、巡检、诊断包、运维和用户手册。
- 安装包、版本清单、验收报告和交付培训。

退出标准：所有发布门禁有自动化或签字证据；不存在未豁免 P0；P1 有明确关闭或合同豁免；能够从备份恢复到可服务状态；版本可在准生产环境完成升级。

总估算：单院生产版约 14–21 周；若先做受限可售试点并明确砍掉 MPI、智能问数、区域能力和高级运营，可在完成 Gate 0 后集中 6–8 周形成首个试点版本。区域生产能力通常还需额外 10–16 周用于组织模型、区域 MPI、跨院数据共享、容量与容灾。

## 10. 发布门禁清单

达到“单院生产发布”前，必须同时满足：

- [ ] 所有业务 API 受身份认证保护，RBAC 与跨租户负向用例通过。
- [ ] 数据源网络出口和 SSRF 防护通过测试，凭据全生命周期可审计。
- [ ] 至少一条真实数据端到端链路连续稳定运行并有故障恢复证据。
- [ ] 真实质量执行器、资产元数据和真实通知已接入，不使用 DEMO 事实源。
- [ ] 数据库版本迁移、备份、恢复、升级和回滚完成演练。
- [ ] TLS、非 root、资源限制、密钥管理、日志脱敏和安全响应头生效。
- [ ] CI 构建不可变制品，测试、SBOM、Secret、依赖和镜像扫描通过。
- [ ] 性能、长稳、故障注入、并发、多租户和灾备测试达到约定指标。
- [ ] 监控、告警、巡检、诊断和死信恢复可由实施/运维人员完成。
- [ ] 产品菜单只展示已授权且可用能力，所有全局筛选和导出真实生效。
- [ ] 安装、配置、网络、备份、升级、应急、用户和验收文档齐全。
- [ ] 客户范围、容量、RPO/RTO、保留期、合规责任和暂缓项形成签字基线。

## 11. 最终建议

不要继续横向增加更多静态页面。下一阶段应围绕一个可出售的最小闭环收敛：

> 单院身份与租户 → 凭据安全 → 前置机/真实数据源 → SeaTunnel → 目标库 → 真实质量规则 → OpenMetadata 资产 → 问题闭环 → 通知 → 监控与验收证据。

这条链完成之前，优先级高于智能问数、复杂运营驾驶舱和更多组件展示。完成后再以相同身份、租户、审计和适配器规范接入 Superset、DB-GPT、MPI/MDM 与数据服务，才能避免形成多个割裂的独立系统。
