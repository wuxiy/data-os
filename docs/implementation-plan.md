# data-os 实施计划

> 版本：1.0
> 日期：2026-08-03
> 推荐周期：20 周（4—6 人小团队）
> 技术基线：[data-os 技术架构设计](./technical-architecture.md)
> 计划口径：W1 为项目正式启动后的第一个完整工作周

## 1. 交付目标

20 周交付一个可在首家医院试运行的 MVP，而不是只完成组件安装。最终必须形成以下闭环：

```mermaid
flowchart LR
    A["源系统与前置节点"] --> B["L0 原始证据"]
    B --> C["L1—L4 数据模型"]
    C --> D["资产、标准、质量与血缘"]
    D --> E["MPI / 主数据"]
    E --> F["看板、问数与数据服务"]
    F --> G["运营、验收与证据包"]
```

MVP 交付范围：

- 1 家医院，5—8 类数据源或源系统，50—100 张表。
- 1 个前置节点，数据库批量 + 1 种增量/CDC + 文件/HTTP/SFTP/HL7 中至少 1 种前置协议。
- L0—L4 分层、dbt 模型、资产目录、血缘、标准映射、质量问题闭环。
- 患者 MPI + 机构/科室/人员至少 1 个通用主数据域。
- 嵌入式 Superset 看板、智能问数 Beta、运营与交付中心。
- Compose 开发/PoC 包、Helm 生产包、离线包、备份恢复和升级回滚记录。

## 2. 实施原则

1. **先验证外部条件，再承诺工期**：真实网络、账号、日志权限、协议样本是 G0 硬门槛。
2. **先做一条垂直链，再铺功能面**：W6 前必须跑通源→L0→Doris→dbt→质量→门户→看板。
3. **门户拥有业务体验，组件拥有执行事实**：不使用 iframe 拼接 OpenMetadata、DolphinScheduler 或 DB-GPT 原生界面。
4. **模板优先**：首院每完成一种稳定接入，必须沉淀为带验证规则、容量参数和错误解释的模板。
5. **发布可逆**：任务、标准、映射、dbt、MPI 和组件版本都要有明确回滚目标。
6. **每个里程碑有机器证据**：测试报告、运行记录、checksum、截图、日志和对账单进入交付证据包。

## 3. 团队与职责

推荐 5 人核心团队；甲方需提供业务负责人和各源系统接口人。

| 角色 | 投入 | 主要责任 |
|---|---:|---|
| 技术负责人 / 后端 A | 1.0 FTE | 架构、控制面、适配器、代码评审、BOM、风险决策 |
| 数据平台工程师 B | 1.0 FTE | SeaTunnel、Doris、dbt、DolphinScheduler、数据分层和性能 |
| 前端 / 全栈工程师 C | 1.0 FTE | 统一门户、BFF 契约、Superset 嵌入、交互验收 |
| 医疗治理 / 实施工程师 D | 1.0 FTE | 源梳理、标准映射、质量规则、MPI 标注、甲方协调和培训 |
| QA / DevOps 工程师 E | 0.8—1.0 FTE | 自动化测试、部署、离线包、监控、备份恢复和验收证据 |
| 产品负责人 | 0.5 FTE | 范围、优先级、原型验收、里程碑签字 |
| 甲方项目负责人 | 每周至少 0.5 天 | 权限协调、业务确认、用户验收和问题升级 |

只有 3 人时，不压缩同样范围到 20 周：优先延期 DB-GPT、区域能力和第二个主数据域，或将周期延长到 28—32 周。

| 工作 | A 技术 | B 数据 | C 前端 | D 实施 | E QA/DevOps | 产品/甲方 |

| 控制面与适配器 | A/R | C | C | I | C | I |
| 数据链路与模型 | A | R | I | C | C | I |

`A` 最终负责、`R` 执行、`C` 协作、`I` 知会。启动会第 1 天必须把角色映射到真实姓名，未到岗角色由产品负责人明确合并承担，不允许责任空缺。

## 5. 分阶段执行计划

### 5.1 P0：启动与风险清零（W1—W2）

#### 工作包

| P0-02 | 验证数据库只读账号、日志/CDC 权限、前置协议和脱敏样本 | D+B | W1-D3 | 权限验证记录、真实样本 |
| P0-03 | 复用 data-ops Doris、Keycloak、部署/DR 资产并列差异清单 | A+E | W1-D4 | 复用清单和不兼容项 |
| P0-04 | 冻结 Java/Node/Python、SeaTunnel、Doris、dbt、OM、Superset、HAPI、DB-GPT 的 BOM | A | W2-D5 | `bom.yaml` 设计基线与兼容报告 |
| P0-05 | 跑通 SeaTunnel→Doris、dbt-doris、dbt→OpenMetadata 制品摄取 | B | W2-D4 | 自动化 smoke 与日志 |
| P0-06 | 跑通 Superset Guest Token 嵌入、DB-GPT 数据问答、HAPI MDM 规则样例 | A+C+D | W2-D4 | 3 个 spike 记录 |
| P0-07 | 冻结领域 ID、API 错误模型、Outbox、Edge 上传协议 | A+C | W2-D5 | OpenAPI 与 ADR |
| P0-08 | 用现有高保真原型完成 5 名甲方用户任务走查 | C+D | W2-D5 | 问题清单与页面优先级 |

#### G0 退出门槛

- 至少 1 个真实数据库和 1 个真实前置协议在目标网络中读取成功。
- 至少 1 条数据完成 SeaTunnel→L0/Doris→dbt→OpenMetadata 全链路。
- Superset 后端换 token 嵌入成功，浏览器不出现服务账号。
- HAPI MDM 在脱敏样本上产生 MATCH、POSSIBLE_MATCH、NO_MATCH 三类结果。
- 每个失败 spike 已形成明确回退方案和对周期的影响；未知项没有“先做再说”。

若源权限或协议样本未通过，项目进入依赖阻塞，不启动 P1 数据接入排期。此举是保护交付，不是技术失败。

#### 工作包

|---|---|---|---:|---|

| P1-02 | 实现源、连接、任务、运行四个核心 API 与接入向导 | A+C | W4 | OpenAPI 合约测试、首表录屏 |
| P1-03 | SeaTunnelAdapter + DolphinSchedulerAdapter 最小闭环 | A+B | W4 | 发布、启动、状态、失败、重试记录 |
| P1-04 | L0 manifest、L1 Doris 装载、幂等与对账 | B | W4 | 重复提交与批次对账测试 |
| P1-05 | dbt 项目骨架、L1→L2 模型、10 条质量规则 | B+D | W5 | dbt 制品和失败门禁 |
| P1-06 | Edge Node 最小包：SQLite WAL 状态库、文件 spool、上传、心跳、配置版本 | A+E | W5 | 断网、进程/机器重启、磁盘阈值、checksum 测试 |
| P1-07 | 门户驾驶舱、任务详情、质量异常和看板垂直切片 | C | W5 | 1280/1440 桌面测试 |

#### G1 退出门槛

- 10—20 张真实或等价脱敏表完成全量和一种增量方式。
- 标准源首表接入中位时长 ≤30 分钟；安装到可用 ≤60 分钟。
- 10 条规则中任一失败可生成问题、责任对象和复检记录。
- Edge Node 断网 24 小时不丢数据，恢复后重放并完成对账。
- SeaTunnel、dbt、OpenMetadata 或 Superset 任一模拟不可用时，门户降级行为符合架构文档。
- 甲方能在一个演示故事中看到“接入—治理—结果”，而不是多个组件页面。

### 5.3 P2：治理与模型工程（W7—W10）

#### 工作包

- 扩展到 5—8 类源、50—100 张表；沉淀至少 3 个接入模板。
- 完成 L1 技术标准、L2 医疗语义、L3 核心主题和 L4 首批指标数据集。
- 实现标准版本、字段映射、样例验证、影响预览、评审与发布。
- 实现双入口单身份质量规则：dbt 构建门禁 + 门户持续质量，统一 `quality_rule_id`。
- 接入 OpenMetadata 资产、字段、Owner、术语、dbt 血缘和测试结果。
- 完成问题指派、接单、处理、复检、退回、关闭和 SLA 逾期。
- 完成数据资产、治理驾驶舱、标准、映射、质量、血缘/影响页面的真实 API 替换。

#### G2 退出门槛

- 任一 L4 指标能下钻到 L3/L2/L1、dbt tag、源表和 L0 证据。
- 破坏性 schema 变更能列出受影响的数据集、规则、看板或 API，并阻止自动发布。
- `issue_id → dataset_id → rule_id → owner_assignment_id → ticket_id → evidence_id` 全链可核对。
- OpenMetadata 停止 2 小时后，数据链路继续；恢复后 Outbox 无丢失并补齐元数据。
- 50—100 张表连续 7 天运行，任务成功率达到双方在 G0 冻结的 SLA。

### 5.4 P3：MPI 与主数据（W11—W13）

#### 工作包

| ID | 工作 | 责任人 | 完成周 |
|---|---|---|---:|
| P3-01 | 患者字段标准化、blocking、确定性规则和候选区间 | D+B | W11 |
| P3-02 | HAPI FHIR Patient/Organization/Practitioner 资源与 MDM 规则 | A+D | W11 |
| P3-03 | crosswalk、黄金值、survivorship 和 `mpi_link_version` | A+B | W12 |
| P3-04 | 候选对比、确认/拒绝、合并/拆分、撤销、影响预览 | A+C | W12 |
| P3-05 | 机构/科室/人员至少一个主数据域的版本和发布回执 | D+A | W13 |
| P3-06 | 脱敏标注集评估和双胞胎/新生儿/未知患者边界测试 | D+E | W13 |

#### G3 退出门槛

- 自动匹配 precision、候选 recall 和人工复核量分别报告，不能只给一个综合准确率。
- 误合并可拆分，拆分后历史数据仍能解释当时的 `mpi_link_version`。
- 自动规则不会覆盖人工确认；未验证的概率结果不能自动发布黄金记录。
- 至少 5 名业务用户能在 3 分钟内完成一条候选处理，任务成功率 ≥90%。

### 5.5 P4：消费与统一体验（W14—W16）

#### 工作包

- Superset：看板目录、后端 Guest Token、门户筛选、口径说明、最近更新时间和原生诊断深链。
- 数据资产：检索、详情、血缘、质量、Owner、消费情况和来源证据。
- DB-GPT Beta：只读数据源、问答流、取消、SQL 限制、数据集/口径/时间证据、反馈。
- 数据服务：登记首批查询 API/导出产品，绑定数据合同、责任人和 SLA。
- 管理驾驶舱：覆盖率、准时率、质量得分、MPI 成效、数据服务使用量和闭环率。
- 完成剩余接入向导、任务详情、前置节点、问题闭环、数据合同与变更页面。

#### G4 退出门槛

- 浏览器不持有 Superset 服务账号、数据库凭据或 DB-GPT/模型密钥。
- 看板、资产和问数回答共享 `dataset_id`、指标口径和责任人，不形成三套目录。
- DB-GPT 返回的每条结果都带查询编号、SQL、数据集和最大数据时间；超范围查询被拒绝或截断。
- Superset 或 DB-GPT 不可用时，固定治理和数据链路不受影响。
- 5 名技术用户和 3 名业务用户完成端到端任务测试，成功率 ≥90%。

DB-GPT 若未通过只读、证据和降级门槛，标记为 Beta 并从正式验收范围移出，不拖延 MVP 主链路。

### 5.6 P5：运营与交付工程（W17—W18）

#### 工作包

- 完成 `platformctl` 的 preflight/install/status/backup/restore/upgrade/rollback/diagnose。
- 完成 Compose、单节点 K3s 和 3 节点 K3s 配置语义对齐；至少实测前两种。
- 建立任务成功率、延迟、积压、Edge 磁盘、Doris compaction、Outbox 和组件健康看板。
- 完成结构化日志、中文错误解释、告警到责任对象的映射。
- 制作离线镜像包、checksum、BOM、许可证清单、初始化数据和回滚包。
- 演练 PostgreSQL、对象存储、Doris 元数据/数据和应用配置的备份恢复。
- 输出实施手册、管理员手册、业务操作手册、故障手册和培训材料。

#### G5 退出门槛

- 全新环境 60 分钟内安装完成并生成机器检查记录。
- 控制库 RPO ≤15 分钟、RTO ≤4 小时的恢复演练通过。
- 应用、组件、采集版本和 dbt 模型各完成一次回滚。
- 诊断包不包含明文凭据、患者明细或模型密钥。
- Edge Node 72 小时容量计算和恢复后 2 倍追平压测通过。

### 5.7 P6：试运行与验收（W19—W20）

#### 工作包

- 冻结候选版本；除 P0/P1 缺陷外不再增加范围。
- 连续 14 天运行，按日核对数据量、延迟、质量、积压和失败恢复。
- 以合同峰值 2 倍执行性能和容量测试。
- 组织技术用户、治理用户、业务用户三类 UAT 和培训。
- 输出已知限制、遗留风险、生产化建议和下一阶段 backlog。
- 生成并签收安装、运行、质量、MPI、性能、恢复、回滚和用户验收证据包。

#### G6 最终验收

| 维度 | 验收标准 |
|---|---|
| 接入 | 5—8 类源、50—100 表，首表中位时长 ≤30 分钟 |
| 稳定性 | 连续 14 天达到 G0 冻结 SLA；失败 5 分钟内可见 |
| 边缘 | 72 小时容量核算，24/72 小时场景完成，恢复追平 ≥2 倍日常速度 |
| 治理 | 标准、映射、质量、血缘、问题和责任链完整闭环 |
| MPI | 标注集报告、人工复核、合并/拆分/撤销全部通过 |
| 使用 | 5 名技术 + 3 名业务用户任务成功率 ≥90% |
| 运维 | 安装、备份、恢复、升级、回滚均有机器记录 |
| 交付 | 文档、离线包、BOM、培训、已知限制和证据包齐全 |

## 8. 测试与验证策略

### 8.1 自动化层级

- 单元测试：领域状态机、幂等键、映射、SLA、MPI 操作和错误归一。
- 模块边界测试：禁止跨模块直接依赖内部包或写表。
- 合约测试：Portal API、Edge API 和所有 Adapter 的成功/错误/超时返回。
- Testcontainers/集成测试：PostgreSQL、对象存储、Doris 关键路径；重组件使用每日共享集成环境。
- 端到端测试：接入、质量问题、MPI、Superset 嵌入、问数证据和交付包。
- 故障注入：断网、重复消息、任务崩溃、对象存储/OM/Superset/DB-GPT/HAPI 不可用。

### 8.2 必测矩阵

| 类别 | 场景 |
|---|---|
| 正常 | 全量→增量、文件去重、HL7 ACK、L0→L4、问题闭环、MPI、看板 |
| 故障 | Edge 断网/重启/磁盘阈值、SeaTunnel 恢复、组件不可用、升级失败 |
| 数据 | 重复、乱序、删除、迟到、Schema 增删改、无主键和超大表 |
| 医疗边界 | 新生儿、未知患者、双胞胎、曾用名、手机号复用、跨机构执业 |
| 规模 | 合同峰值 2 倍、50—100 表并发、72 小时积压追平 |
| 回滚 | 组件、数据库迁移、采集版本、dbt、标准映射、MPI 拆分 |

完成不等于“页面能打开”。每个工作包必须至少有：需求/契约、实现、自动化测试、运行证据、故障行为、运维说明和回滚目标。

## 11. 范围变更规则

以下变更会改变架构或 20 周承诺，必须重新评估：

- 从单院 MVP 变为多院区域试点；
- 增加 Spark/Flink/Kafka/Iceberg/Trino 或要求纯湖仓；
- 要求任意源实时 exactly-once、双向回写或 PACS 像素归档；
- 正式等保/密评、跨机构细粒度授权提前进入本期；
- 源数量超过 8 类、表超过 100，或私有接口超过 20%；
- 甲方要求移动端或同时重做全部原生组件管理能力。

范围变更单必须包含：业务价值、组件和模块影响、数据迁移、测试增量、工期、人力、回滚和不做的代价。没有这些信息不进入当前迭代。
