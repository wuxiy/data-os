# EP 域数据面扩展计划：EP_TEST 148 表盘点与批次接入（G16a/G16b）

> 日期：2026-09-02
> 状态：已批准（本对话裁决）
> 依据：G1–G15 验收事实、`docs/decision-intelligence-next-stage-plan-20260901.md` §十二裁决记录
> 阶段定位：核心职责 1/2/4——快速开发系统工作流程、打通基础功能与运行链路、完善 ToB 端 API 接口

## 一、背景与裁决链

- G15 收官（决策权已切 v1+v2 混合引擎，`docs/validation/gate-mpi-g15-20260902.md`）；
- G15B 产品准入因业务 Owner 短期不可得记**短期 No-Go**，语义线 G16/G17 parked；
- 当前真实数据面全部压在 **2 张 EP 表**上（`EP_MZ_CFZB` 11,373 行 / `EP_MZ_YPCFMX` 12,215 行），而 DM 源库 `EP_TEST` schema 共 **150 张表**未盘点；
- Data API 仅 1 个数据集（prescription-daily-summary），消费面扩容缺数据底座。

新主线：**EP 域做厚**——盘点剩余 148 表，按批次把高价值表接入已验证的完整链路（采集→质量→资产血缘→消费）。全部为已验证模式的复制，不引入新技术面。

## 二、明确不做

- 不新增微服务、数据面、采集引擎或前置机组件；
- 不做语义层/指标 Manifest（parked，等业务 Owner）；
- 不做驾驶舱补真（No-Go 后固定看板归 Superset 的裁决不变）；
- 不做全量 150 表入仓（字典表/空表/日志表不选题直接入）；
- 深度测试/安全/生产加固继续归口 `docs/deferred-hardening-backlog.md`。

## 三、G16a：EP_TEST 148 表盘点与选题（约 1 周，3–5 人日）

### 3.1 前置检查

- dev 机可达 DM `jdbc:dm://192.168.17.76:5236?schema=EP_TEST`；不可达时降级为既有文档底账初选，连源后复核。

### 3.2 交付物

- `docs/ep-domain-inventory-<date>.md`：逐表记录表名/注释/行数/最大业务时间戳/列清单摘要/**是否含患者身份字段**（姓名、卡号、联系方式）；
- 首批选表裁决：5–10 张高价值表（判据：行数非空、业务含义明确、新鲜度活、有维度或身份价值）；
- 身份字段表专门标记，作为 T5b 条件项触发判据；
- `docs/validation/gate-ep-inventory-g16a-<date>.md`：盘点结论与选表依据。

### 3.3 验收清单

- [ ] 148 表（150 减已入 2 张）全部有行数与新鲜度记录，无遗漏；
- [ ] 含身份字段的表逐一标记到列级，可直接支撑 T5b 判据评估；
- [ ] 首批选表有明确业务理由，排除空表/死表/纯字典表；
- [ ] 盘点查询不写源库（只读系统视图与 COUNT/MAX 抽样）。

## 四、G16b：首批全链接入（1.5–2 周，10–15 人日）

### 4.1 每张表的交付链（全部复用已验证模式）

1. **采集**：SeaTunnel JDBC 作业（复用 CFZB 模板，增量占位符按 `TO_TIMESTAMP(REPLACE(SUBSTR('${last_success_time}',1,19),'T',' '))` 规整）；
2. **落仓**：Doris `ods_ep` 新表，writer 账号沿用既有三重授权；
3. **质量**：dbt 规则（主键唯一/非空/值域/外键关系，复用 `ep_edge` 模式）并注册进控制面质量域；
4. **资产与血缘**：OM 摄取脚本登记 + dbt 产物列级血缘（G6/G7 兼容链，1.7+dbt-mysql 产物）；
5. **消费**：至少 1 个新 Data API 数据集（无 PHI 聚合口径，走 G13 发布/配额/审计面）；Superset 图表按需可选。

### 4.2 T5b 条件项（G16a 标记到身份表时触发）

- 第二身份流入仓后按 `docs/mpi-recalibration-runbook.md` 执行重标定（估计器/漂移报告/dev 基线全部现成）；
- 重标定报告**如实标注「同库跨表弱多源」局限**：同一 DM 库的跨表身份流与真实多源系统存在分布差异；
- 判据不满足（无身份表、或分布差异不足以支撑结论）则 T5b 继续留备忘条目，不造数据、不放宽判据。

### 4.3 验收清单

- [ ] 首批每张表完成一次全量+增量采集运行，行数与源库对账一致；
- [ ] 质量 dbt 规则全绿并在控制面可查，失败路径有真实证据；
- [ ] OM 资产可查、列级血缘可追，列数与源表一致；
- [ ] 新 Data API 数据集通过 G13 既有配额/审计/权限面调用验证，无 PHI 明细；
- [ ] （若触发）T5b 重标定报告落档，弱多源局限如实记录；
- [ ] control-plane Maven、quality-runner pytest、portal tsc/vitest/QA/build 全绿；
- [ ] dev 环境完成一次 `源库 → SeaTunnel → Doris → 质量 → OM → Data API` 证据链验收。

## 五、节奏与后续

- G16b 之后批次（G16c…）同模式滚动，不另立大计划；每批独立 Gate、独立验收文档；
- 并行独立小项（随本主线首个提交落地）：ProductScopeNotice 修正 + QA 锁同步，把 MPI、资产、分析、数据服务从「规划/待接入」改为与 G3/G4/G6/G13 一致的已验收口径。

## 六、风险与回滚

- **DM 可达性**：源库不可达时 G16a 降级为文档初选，不阻塞计划文档与 ProductScopeNotice 交付；
- **表结构未知**：盘点前不承诺任何具体表；选题裁决以盘点事实为准，不预设业务猜测；
- **回滚**：每张新表独立作业/独立规则，坏表停作业即可，不影响既有 EP_MZ_CFZB/EP_MZ_YPCFMX 链路；Data API 新数据集独立发布，可单独下线。
