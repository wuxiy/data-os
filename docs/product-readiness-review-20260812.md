# data-os 产品级与轻量投入复审

审查日期：2026-08-12

审查范围：功能实现、真实业务闭环、轻量部署、失败恢复、运维可操作性和验证证据。

明确排除：安全、认证、权限、合规、隐私和漏洞风险不纳入本轮判断。

## 一、结论

当前版本**尚未达到完整产品级**，但已经超过普通静态原型，形成了一条可继续试点的真实控制面骨架：

`数据源登记/检查 → 采集任务 → 外部运行 → 状态同步/水位 → 质量复检 → 治理问题 → 处理说明/通知`

这条链路的控制面 API、数据库迁移、状态更新、幂等键、检查点和质量问题回写均有实现；Java 控制面测试也相对完整。可是，真实 LIS/EMR/手术端点、Doris 目标和院方外部依赖没有在仓库中形成可重复的跨组件验收，门户还有大量模块明确停留在演示或待接入状态。

最终定位如下：

| 投入方式 | 判断 | 说明 |
| --- | --- | --- |
| 产品演示、技术联调 | 通过 | 真实 API 与失败态可展示，演示数据有显式边界 |
| 已有平台团队配合的单院受控试点 | 有条件通过 | 只承诺采集 + 治理 + 质量闭环，并先完成真实端点交接和一次跨组件验收 |
| 业务人员日常使用的轻量门户 | 暂不建议 | 标准、资产、MPI、分析、问数等入口不是实时业务功能，配置和部署也偏技术化 |
| 完整医疗数据产品发布 | 未通过 | 产品宣传范围与真实实现范围不一致，交付、恢复和发布证据不完整 |

## 二、能力盘点

### 1. 已具备真实实现的核心能力

#### 数据接入与运行控制

已实现的控制面能力包括：

- 按租户/机构保存和查询数据源；
- JDBC、HTTP、FHIR 来源检查，并将失败显式记录为不可用；
- 创建任务、保存版本化 JSON 配置、启用/暂停/归档；
- 提交运行、同步状态、失败重试和运行详情；
- 运行幂等键、活跃运行冲突、状态条件更新；
- 任务成功后推进检查点，失败不推进水位；
- `${last_success_time}`、`${run_start_time}`、`${data_os_run_id}` 等运行参数插值。

主要证据：`SourceService.java`、`JobService.java`、`JobConfigService.java`、`RunService.java`、`RunStatusSyncService.java`、`IngestionCheckpointRepository.java`。

这部分已经不是页面假动作，门户也有真实 API 调用和连接失败/空数据/重试反馈。限制在于：配置仍偏原始 JSON，来源没有完整的编辑/删除生命周期，真实来源端点、凭据、表结构和 Doris 目标仍需院方配置。

#### 治理问题与质量闭环

控制面已实现：

- 治理指标和问题队列查询；
- 问题详情、处理说明、事件记录；
- 发起质量复检、轮询执行器、同步执行批次；
- 质量通过后自动关闭问题，失败/取消后退回；
- 失败样本证据、责任人通知和幂等投递；
- 质量 finding 按来源和执行批次去重，并支持“通过但没有问题”的观察记录。

质量运行器具备 FastAPI 提交/查询/取消、dbt 执行、队列租约、超时、取消、重启后的 stale 重排队、证据读取、制品保存和清理逻辑。

这条链路的产品价值已经明确，当前最大问题是“代码存在”与“完整跨组件可交付”之间仍有距离：仓库没有持续集成中的真实 PostgreSQL + Doris + dbt + RustFS + 控制面回写验收。

#### 平台运维入口

平台运维页可以读取 SeaTunnel、DolphinScheduler、RustFS 的聚合状态并提供技术入口。但它本质上是状态查询和外链，不是安装、升级、备份、恢复、故障修复或任务运维中心。

### 2. 尚未达到真实产品能力的模块

生产构建中，以下页面会通过 `DemoDataBoundary` 关闭静态样例或显示“待接入真实服务”：

- 管理首页真实指标；
- 数据标准；
- 标准映射及保存；
- MPI 候选审核和关联确认；
- 数据资产、技术视图和影响清单；
- 分析看板及专业编辑；
- 智能问数及专业工作区；
- 治理责任链和治理趋势。

这些页面不是“功能不稳定”，而是目前没有对应的真实 BFF/API 或持久化副作用。源码中的“保存映射”“确认建立关联”“生成影响清单”等动作仍是本地状态或 Toast 提示，不能作为业务事实。

另外，主导航中的“数据服务”“运营中心”“交付中心”“系统设置”没有真实路由，只显示未接入提示。门户当前可用范围在 `prototype/src/App.tsx:82-128` 已经被代码明确收窄为数据接入、治理驾驶舱和质量闭环。

### 3. 真实数据闭环的边界

仓库提供了脱敏回放源，已验证 LIS HTTP 合同、健康检查和 since 水位请求；这证明接口合同可以工作，但不等于真实临床系统已接入。

当前仍缺少现场证据的部分包括：

- 真实 LIS、EMR、手术系统端点和连接账号；
- 真实源表/接口字段、增量语义和数据样本；
- SeaTunnel 真实版本执行器到 Doris 的一次成功与一次失败重跑；
- 真实质量规则在 Doris 上执行并把证据/制品回写控制面；
- 院方通知网关的投递、失败重试和接收端幂等。

因此不能把回放源、合成 Doris 或开发 RustFS 验收表述为真实临床生产验收。

## 三、影响轻量使用的关键问题

以下分级只针对功能和投入使用，不涉及安全问题。

### P0 / 范围级阻断

1. **真实临床链路还没有交付证据。** 如果目标是“投入真实医院数据”，至少要完成一个真实来源到 Doris、质量规则、治理问题和通知的闭环；现阶段只能证明协议、代码和合成环境。

2. **完整产品范围没有实现。** 如果产品范围包含标准、映射、MPI、资产、分析、问数、数据服务和交付中心，则这些模块仍是原型/入口，不能按完整产品发布。若将首期范围明确收窄为采集 + 质量治理，则该项可从阻断项降为后续版本。

3. **轻量部署不是单命令产品包。** 生产基础 Compose 只包含 PostgreSQL、control-plane、quality-runner、portal、Prometheus；Doris、RustFS/S3、通知端点、OIDC、SeaTunnel 制品和可选 DolphinScheduler 需要另行准备。首次部署还要人工编辑环境、准备制品、创建外部数据库/账号、初始化调度器和做现场验收。

### P1 / 试点前应补齐

1. **跨组件 smoke 尚未成为自动门禁。** 需要至少持续验证：回放/真实来源 → SeaTunnel → Doris → 状态与检查点 → quality-runner/dbt → 样本/制品 → control-plane → 治理问题 → 通知接收器。当前 CI 没有 `docker compose up`、真实迁移、质量执行、容器重启或外部组件联调。

2. **外部采集提交存在崩溃窗口。** 控制面先写 `SUBMITTING`，再调用外部执行器。如果外部提交成功而控制面在写回外部 ID 前崩溃，恢复逻辑可能把记录标记为阻断，人工重试可能重复提交。当前幂等键主要保护控制面，尚未证明 SeaTunnel/DolphinScheduler 会按 `dataos_run_id` 查询并复用已提交实例。

3. **质量运行器 stale 重排队没有执行 fencing。** 运行器重启后可将旧 `RUNNING` 重新排队；没有执行代次或持久化进程租约时，旧 dbt 子进程和新 worker 可能短暂并发执行。最终状态更新有条件保护，但外部执行副作用仍可能重复。

4. **UNKNOWN 没有统一的人工接管语义。** 采集和质量执行器都可能出现外部批次丢失/不可确认；质量侧缺少明确的最大持续时间、人工对账状态和终止入口，可能长期停留在中间态。

5. **质量制品链路没有完全回到门户。** quality-runner 可以生成 `artifactUri`，但控制面 HTTP 适配和质量运行模型没有完整持久化/返回该地址，治理详情主要能看到样本 JSON，不能稳定追踪对象存储制品。

6. **日常操作偏技术化。** 数据源检查、任务配置和临床模板虽有校验，但核心配置仍是 JSON；没有面向业务人员的连接参数向导、源编辑/删除、补数窗口和明确的批次回放入口。

7. **恢复与升级操作没有平台级闭环。** 文档提供 `pg_dump` 和应用镜像回滚说明，但没有标准化 `pg_restore`、恢复后校验、质量/调度器/对象存储数据恢复、RPO/RTO 或整个平台演练。`platformctl` 只在架构文档中规划，当前仓库不存在该工具。

### P2 / 可在试点后增强

- 治理责任链、趋势、资产血缘和影响分析的真实数据聚合；
- 前端筛选器真正影响 API 查询，而不是只显示提示；
- 失败重试从整页刷新改为局部请求，保留当前表单、筛选和选中项；
- 生产静态服务器深链、`/assets` 路径和技术深链的发布后自动 smoke；
- quality-runner、SeaTunnel、DolphinScheduler、PostgreSQL 的业务运行指标及积压告警；
- PostgreSQL 真迁移、容器重启、长时间运行和容量验证；
- 质量 finding、通知和治理状态迁移的更严格合同测试。

## 四、轻量投入评估

### 部署投入

开发基线至少包含 control-plane、RustFS、RustFS 初始化、quality-runner、通知接收器和 portal；启用 SeaTunnel 后增加执行器，启用 DolphinScheduler 后还要叠加独立数据库、初始化器、API、Master、Worker、Alert、Token 轮换器等组件。

生产基础组合虽然能通过 Compose 配置解析，但完整单院形态仍然是多个 Compose overlay + 外部系统。`deploy/production/README.md` 要求按顺序准备镜像、门户静态包、环境变量、通知文件、SeaTunnel 离线包、Doris、RustFS/S3，并人工启动和验收。

所以它适合“有平台工程师按手册交付”的单院试点，不适合“业务团队拿到包即可自行轻量投入”。

### 运维投入

现有平台运维页只能回答“组件是否能探测到”；不能完成：

- 安装预检和依赖缺口汇总；
- 任务积压、质量规则失败率、通知积压和水位停滞诊断；
- 备份/恢复与恢复结果确认；
- 版本升级、迁移前后兼容检查和整个平台回滚；
- 一键生成跨容器诊断包。

架构文档计划的 `platformctl` 能力尚未实现，当前轻量使用的隐性成本主要落在平台工程师身上。

## 五、验证证据与可信度

| 验证 | 结果 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| `mvn -B -ntp -f services/control-plane/pom.xml test` | 80 项通过 | 控制面 API、状态机和适配器契约较完整 | 真实 PostgreSQL、真实 SeaTunnel/DS 和跨容器闭环 |
| quality-runner pytest | 临时干净环境 4 项通过 | 规则目录、证据分类/脱敏基础逻辑 | FastAPI、队列租约、dbt、Doris、RustFS、重启行为 |

| `npm run build` | 通过，Vite 产物生成 | 当前依赖可构建、静态资源可打包 | 发布服务器回退和真实 API |
| 回放源 HTTP smoke | 通过 | LIS 合同、healthz、since 水位 | 真实临床系统和真实数据质量 |

测试证据总体说明：控制面单元/API 层较扎实，跨组件和质量运行器行为测试明显不足。H2 迁移通过不能替代 PostgreSQL 真实迁移；配置解析通过不能替代 `compose up` 后的功能验收。

## 六、最小补齐路线

如果目标是尽快得到“可轻量投入的单院试点”，建议冻结产品范围，只补下面五件事：

1. **明确首期承诺**：只对数据接入、采集运行、治理问题、质量复检和通知负责；未接入模块在门户中改为清晰的“规划中/不可用”入口，避免业务误用。
2. **完成一条真实端到端链路**：选一个 LIS 或 EMR 来源，完成真实端点、字段、水位、Doris 目标、SeaTunnel 作业、质量规则、治理问题和通知验收；同时保留回放源作为 CI fixture。
3. **补一次可重复交付命令**：先不做复杂平台，至少提供 preflight + install + status + smoke 报告，自动检查外部依赖、迁移状态、门户回退、质量运行器 readiness 和通知回执。
4. **修正四个运行语义**：外部提交后的可恢复对账、quality-runner 执行 fencing、UNKNOWN 人工接管、artifact URI 回传。它们直接影响失败后是否会重复、卡死或无法取证。
5. **补最小恢复门禁**：PostgreSQL 空库迁移、备份恢复、控制面/质量运行器重启、一次失败重试、一次通知重投；形成一份机器生成的验收记录。

完成以上五件事后，可以把范围收窄的版本定义为“单院受控试点产品”。在此之前，继续增加标准、资产、问数等静态页面不会显著提高当前可投入程度。

## 七、最终判定

**判定：核心垂直链路具备试点基础；项目整体尚未达到产品级，也尚未达到真正轻量投入标准。**

最准确的产品定位是：

> 有真实控制面、质量闭环骨架和开发验收证据的受控试点基线。

它可以继续投入，但投入对象应是平台工程师主导的、范围收窄的单院试点，而不是面向业务人员的完整医疗数据产品发布。

## 八、按复审建议补齐后的复核

本轮已把可以在仓库内直接完成、且不依赖真实院端点的建议项落地：

- 门户首期范围和演示边界已显式呈现，未接入模块不会把保存、确认、生成等本地动作包装为真实副作用。
- 采集运行增加稳定 `data_os_run_id` 的外部对账/人工关联、UNKNOWN 接管和确认不存在；质量运行增加 UNKNOWN 重查/确认不存在。
- quality-runner 增加 `execution_generation` fencing，旧代次不能 heartbeat、finish 或保留失效制品；`artifactUri` 已贯通运行器、控制面和门户详情。
- 新增 `deploy/production/scripts/platformctl`，提供 preflight、install、status、smoke、backup、restore、restart，并保留显式的占位值失败和恢复确认门槛。

补齐后的验证结果为：control-plane Maven 85 项通过，quality-runner pytest 8 项通过，前端 build/mock/interaction smoke 通过，生产 Compose `config --quiet`、脚本语法和 `git diff --check` 通过。

结论不因此升级为完整产品级：真实 LIS/EMR/Doris/通知网关链路、跨容器重启和真实备份恢复仍没有在本仓库环境中完成证据闭环。因此当前定位更新为“范围收窄后具备受控试点交付基础”，而不是“一份 Compose 即可投入生产”。
