# 医疗数据采集治理运营平台蓝图

> 日期：2026-08-01
> 状态：已批准（见第 17 节，批准后生效）；不包含代码实现
> 适用范围：单体医院数据平台、区域医疗数据平台
> 详细实施基线：[技术架构设计](./technical-architecture.md)｜[20 周 MVP 实施计划](./implementation-plan.md)

## 1. 推荐结论

不建议复制 Databricks 的全部技术栈，也不建议把多个开源系统的原生界面拼成一个“门户”。推荐建设一个医疗业务化的统一产品控制面，借鉴 Databricks 的四个原则：统一工作空间、分层数据、统一资产治理、采集到消费的全链路可观测；底层开源组件只作为可替换的执行器。

首期推荐采用“轻量实时数仓 + 对象证据层 + 湖仓就绪”路线：

- Apache SeaTunnel Zeta 负责数据库批量、增量、CDC 和大规模同步。
- 前置机按场景选择 MiNiFi 或医疗接口引擎，不在每个站点堆叠多个采集运行时。
- Apache Camel 只作为特殊协议适配器的开发库，不作为独立运营平台。
- Apache Doris 负责频繁更新数据、标准层、主题层和交互分析；S3 兼容对象存储保留原始消息、文件、快照与证据。
- dbt Core + dbt-doris 负责 L1—L4 的批量/微批 SQL 模型、构建期测试和转换血缘；它是转换模块，不是完整的数据治理平台。
- PostgreSQL 负责平台配置、工单、主数据流程与审计元数据。
- OpenMetadata 提供资产、术语、血缘和质量元数据底座；门户通过 API 重新组织用户体验。
- HAPI FHIR R4 + MDM 模块承担医疗互操作和患者/人员/机构匹配基础能力；平台自研审核、合并/拆分、版本、发布和回执流程。
- Apache Superset 提供探索和图表能力，以嵌入方式进入统一门户。
- Docker Compose 只用于开发和 PoC；生产使用同一套 Helm 包部署到单节点或三节点 K3s/现有 Kubernetes。

这不是“最少组件数”的方案，而是“最少自研基础设施 + 可分能力包安装”的方案。完整逻辑能力可以存在，但单院不必安装区域平台才需要的每个运行时。

## 2. 建设范围

### 2.1 本期建设

- 数据源、连接、前置节点和采集任务管理。
- 数据库全量/增量/CDC，文件、HTTP、SFTP、HL7 v2/MLLP 等典型接入。
- 原始证据留存、标准化、主题建模、数据质量、血缘与问题闭环。
- 患者/居民主索引，以及机构、科室、人员、术语和值域主数据。
- 数据资产搜索、数据服务、嵌入式 BI、运营驾驶舱和交付验收中心。
- 单院与区域两种租户/机构模型，前置机断网缓存和补传。
- 离线安装、配置检查、备份恢复、诊断包、版本清单和升级回滚。

### 2.2 首期不建设

- 不建设 Spark/Flink/Kafka 组成的通用大数据组件集群。
- 不建设 Notebook、特征库、模型注册、在线推理等 AI/ML 平台。
- 不替代 HIS、EMR、PACS/VNA，也不把 DICOM 像素数据作为首期湖仓主体。
- 不把 OMOP CDM 当作医院运营主模型；它只作为后续科研专题模型。
- 不承诺对任意源系统实现绝对 exactly-once；采用至少一次投递、稳定偏移量和中心幂等。
- 不从零自研概率匹配算法、SQL 查询引擎、调度器、元数据搜索或 BI 引擎。
- PoC 暂不做完整等保、密钥托管和细粒度授权，但 `tenant_id`、机构隔离、数据来源、操作审计和可逆变更模型从第一天保留。

## 3. 架构原则

1. **一个门户，不暴露组件拼盘**：甲方日常操作不进入 SeaTunnel、NiFi、OpenMetadata、Doris 或 Superset 原生控制台。
2. **一套业务对象**：机构、节点、源系统、连接、任务、数据集、规则、问题、主数据、数据产品贯穿所有模块。
3. **原始证据不可丢**：任何标准化结果能定位到原始消息/文件/源记录、采集批次、转换版本和 MPI 映射版本。
4. **单院与区域同一代码路径**：单院只是单租户配置，区域场景增加机构隔离与区域级发布，不维护两套产品。
5. **模板优先，脚本兜底**：常见 HIS/LIS/EMR/PACS 接入做成模板；特殊协议通过受控插件扩展。
6. **执行器可替换**：门户只依赖统一的适配器接口，不把 SeaTunnel/NiFi 的内部对象直接暴露成产品领域模型。
7. **按能力包部署**：核心包、治理包、医疗互操作/MPI 包、边缘包、区域扩展包可组合安装。

## 4. 总体架构

```text
┌────────────────────── 医院/区域用户 ──────────────────────┐
│ 管理者          数据管理员          数据工程师/实施/运维    │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 医疗数据统一门户                                             │
│ 首页｜接入｜资产｜治理｜MPI/MDM｜服务｜分析｜运营｜交付       │
└──────────────────────────┬───────────────────────────────┘
                           │ Portal API / 统一领域模型
┌──────────────────────────▼───────────────────────────────┐
│ 平台控制面                                                   │
│ 连接与模板｜任务版本｜质量与工单｜主数据流程｜指标口径         │
│ 执行器适配器｜事件接收｜状态归一｜告警｜证据包                 │
└──────────────┬───────────────┬──────────────┬────────────┘
               │               │              │
       ┌───────▼──────┐ ┌──────▼──────┐ ┌────▼───────────┐
       │ 采集与编排     │ │ 医疗身份/互操作 │ │ 治理与消费       │
       │ SeaTunnel     │ │ HAPI FHIR MDM │ │ OpenMetadata   │
       │ DolphinScheduler│ │ MDM Workflow  │ │ Superset       │
       │ dbt Core      │ │ Splink（离线）  │ │ 数据服务 API     │
       │ NiFi/MiNiFi*  │ └──────┬──────┘ └────┬───────────┘
       │ OIE*/Camel SDK│        │              │
       └───────┬──────┘        │              │
               └───────────────┼──────────────┘
                               │
       ┌───────────────────────▼───────────────────────────┐
       │ 数据面                                              │
       │ S3 兼容对象存储：原始消息/文件/快照/冷数据           │
       │ Apache Doris：ODS/标准层/主题层/指标层               │
```

主数据流从源到消费单向推进，没有数据回写闭环。门户到执行器是控制流，执行器回传状态和运行事件是观测流；二者不改变源数据事实。

## 5. 组件选型与边界

| 能力 | 推荐 | 明确职责 | 首期边界 |
|---|---|---|---|
| 统一门户与控制面 | 自研轻量 Web + API | 中文业务对象、统一状态、待办、工单、执行器适配、交付证据 | 不重写底层计算、搜索和 BI |
| 控制数据库 | PostgreSQL | 配置、版本、工单、主数据流程、审计、组件独立 schema | 不存大规模分析明细 |
| 数据库同步 | SeaTunnel Zeta | 全量、增量、CDC、多表同步、任务状态和检查点 | 不承担复杂业务工作流和甲方门户 |
| 工作流编排 | DolphinScheduler | 跨 SeaTunnel、SQL、HTTP 和批处理的 DAG、补数、重跑、告警 | 原生 UI 只供高级诊断 |
| 通用前置采集 | MiNiFi C++/Java | 文件、JDBC、水位增量、设备/边缘采集、本地队列、provenance | 真 CDC 或复杂医疗消息按增强模板处理 |
| 医疗接口引擎 | OIE（可选） | HL7 v2/MLLP、FHIR、文件/JDBC、消息监控和重放 | 治理仍较年轻，上线前做兼容性回归；不与 MiNiFi 默认叠装 |
| 特殊协议 SDK | Apache Camel | 自研适配器内部的协议路由、HAPI HL7/MLLP/FHIR 组件 | 不作为面向用户的任务运营台 |
| 实时数仓/查询 | Apache Doris | ODS 当前态、标准层、主题层、指标、交互查询、CDC upsert | 不在首期强制建设纯开放湖仓 |
| SQL 转换与模型工程 | dbt Core + dbt-doris | L1—L4 模型依赖、SQL 转换、构建期测试、文档和制品 | 不负责采集、实时流处理、治理审批、资产目录或主数据 |
| 原始与冷数据 | S3 兼容对象存储 | 原始文件/消息、快照、导出物、证据包、后续 Iceberg | 实现保持可替换；商用分发前单独核对许可证 |
| 元数据治理 | OpenMetadata | 技术元数据、业务术语、资产搜索、血缘、质量结果 | 通过 API 嵌入，不把原生 UI 直接交付给业务用户 |
| 数据质量 | 平台规则模型 + Doris SQL + OpenMetadata 结果 | 规则模板、执行、问题单、责任人、SLA 和趋势 | 首期不额外引入 Great Expectations/Soda |
| MPI/FHIR | HAPI FHIR R4 + MDM | FHIR API、Patient/Practitioner/Organization 规则匹配、黄金资源基础 | 默认 Starter 不是完整生产平台；审核/版本/分发由平台补齐 |
| 概率关联 | Splink（离线） | 标注集评估、阈值分析、批量候选生成 | 不拥有黄金记录，不做未经审核的在线自动合并 |
| BI | Apache Superset | 自助探索、图表、仪表板、轻量语义层 | 嵌入门户，指标口径由平台治理 |
| 观测 | Prometheus + Grafana | 指标、组件诊断和业务 SLO | 首期日志使用 stdout/journald + 保留策略；区域化后再按量启用 Loki/OpenTelemetry |
| 容器运行时 | Compose → K3s/Kubernetes | PoC 快速启动；生产声明式部署、扩缩和回滚 | 两节点不包装成高可用；HA 使用三个控制节点 |

### 5.1 SeaTunnel、NiFi/MiNiFi、Camel 如何分工

三者不能让用户自行选择。平台根据接入模板决定执行器：

| 场景 | 默认执行器 | 原因 |
|---|---|---|
| Oracle/MySQL/PostgreSQL/SQL Server 全量、批增量、CDC | SeaTunnel Zeta | 面向数据同步优化，支持多表、检查点和批流作业 |
| 前置机文件、SFTP、HTTP、设备侧采集，要求小体积和本地缓冲 | MiNiFi | 面向 first mile/edge，具备低资源和本地队列能力 |
| HL7 v2/MLLP、消息 ACK、人工重放和医疗接口监控 | OIE 增强模板 | 医疗接口语义和消息运营能力更直接 |
| 特殊 WebService、私有 TCP、厂商 SDK | Camel 适配器 | 作为库封装协议，便于测试和版本化 |
| 跨任务依赖、补数、SQL 转换、质量规则 | DolphinScheduler | 统一工作流而不重复造调度器 |

NiFi 服务端只在需要可视化编排、集中管理 MiNiFi 或复杂路由时启用。若首个项目的 80% 接入都是数据库同步，不应为了“组件完整”默认部署 NiFi 集群。

决策记录（2026-08-02）：2026-07 的 data-ops 实验项目在真实 dev 环境跑通了 MiNiFi → NiFi → Doris → dbt 全链路，验证了 Doris + dbt 门禁 + SSO 基础设施可行，但同时实证 NiFi 服务端对院内多源、多策略采集体量过重、策略支持不足。据此定案：中心编排固定为 DolphinScheduler，数据库同步固定为 SeaTunnel，NiFi 服务端不作为默认组件；MiNiFi 保留为边缘前置执行器选项之一。data-ops 的 dev 环境基础组件（Doris 集群、Keycloak SSO、部署与 DR 脚本）由本项目复用。

### 5.2 为什么首期推荐 Doris，而不是直接堆齐 Iceberg + Trino + Spark/Flink

医疗源表有大量主键更新、状态变化、撤销和补录。Doris 的 Unique Key/Upsert 模型更直接地承接 CDC 当前态，SQL 服务和 BI 查询也无需再维护一套独立服务层。对象存储仍保留原始证据，因此并未锁死未来湖仓路线。

当出现以下任一明确需求时，再启用 Iceberg 能力包：

- 区域级数据达到数十 TB，并要求冷热分层和低成本长期留存。
- 数据科学、科研或第三方引擎必须直接读取开放表格式。
- 同一份数据要被 Doris 之外的多个计算引擎并发消费。
- 需要快照级历史回放、跨引擎 schema/partition evolution。

升级路径为“对象存储 + Iceberg REST Catalog + Doris 外部 Catalog”；只有 Doris 的联邦查询覆盖不了目标数据源时才增加 Trino。这样不会在首期引入 catalog、compaction、小文件治理和多计算引擎运维。

## 6. 数据分层与事实追溯

Databricks 的 Bronze/Silver/Gold 适合作为质量递进原则，但医疗平台需要显式保留医疗语义与原始证据：

| 层级 | 映射 | 内容 |
|---|---|---|
| L0 原始证据层 | Bronze-0 | HL7/CDA/FHIR 原文、文件、CDC envelope、DICOM 元数据、校验和 |
| L1 技术标准层 | Bronze-1 | 字符集、类型、时间、字段名、主键、删除标志和技术规范化 |
| L2 医疗语义层 | Silver | 医疗标准模型、MPI crosswalk、机构/科室/人员/术语映射 |
| L3 主题层 | Silver/Gold | 患者、就诊、医嘱、检验、检查、费用、手术、护理、运营主题 |
| L4 产品层 | Gold | 指标、标签、患者 360、监管专题、API、文件和报表 |

每条标准化记录至少携带或能关联：

```text
tenant_id
institution_id
source_system_id
source_record_id / message_id
ingest_event_id
raw_object_uri + checksum
event_time / extract_time / receive_time
pipeline_run_id
transform_version
terminology_mapping_version
mpi_link_version
quality_result_id
```

区域平台保留本地身份与区域身份的双层关系：

```text
(tenant_id, institution_id, source_system_id, local_patient_id)
                              │
                              ▼
                     regional_person_id
```

临床事实不因 MPI 合并而覆盖原始患者标识，只附加当时的 `mpi_link_version`。规则升级、误合并拆分或机构退出时可以重新计算关系，而不破坏原始事实。

### 6.1 数据治理底座的事实归属

数据治理不是一个组件，而是若干深模块协作。每类事实只能有一个权威来源，其他系统保存索引或投影，避免标准、规则和血缘在多个后台相互覆盖：

| 事实类型 | 权威来源 | 说明 |
|---|---|---|
| 资产、字段、负责人、业务术语、技术血缘、数据合同、质量结果 | OpenMetadata | 作为治理元数据中心，供统一门户检索、下钻和聚合 |
| 医疗数据标准、值域、代码映射、标准版本与审批状态 | 平台治理注册库（PostgreSQL）+ HAPI FHIR Terminology | PostgreSQL 管流程和版本；CodeSystem、ValueSet、ConceptMap 使用 FHIR 表达 |
| 可执行 SQL 模型、模型依赖、构建期规则 | dbt Git 仓库 | SQL/YAML 与应用代码一样评审、测试、发布和回滚 |
| 数据明细、标准层、主题层、指标结果 | Apache Doris | dbt 和质量执行器在 Doris 上计算，不把明细复制到治理库 |
| 调度依赖与执行历史 | DolphinScheduler | 调用 SeaTunnel、dbt 和治理校验；门户接收归一后的状态事件 |
| 问题单、责任流转、验收证据 | 平台控制库（PostgreSQL） | 与 OpenMetadata 质量结果关联，不在 dbt 中实现人工流程 |

统一门户只依赖平台的治理模块接口，例如“发布标准版本、验证映射、构建模型、校验数据合同、关闭治理问题”。dbt CLI、OpenMetadata 实体和 Doris SQL 都隐藏在实现内，避免前端分别理解三个系统的内部对象。

### 6.2 dbt 选型结论

dbt 可行，并推荐作为 SQL 转换和模型工程的默认实现，但不能被定义为“数据治理底座”的全部。适用边界如下：

| 场景 | 是否使用 dbt | 理由 |
|---|---|---|
| L1 字段重命名、类型统一、清洗 | 是 | SQL 模型可版本化，依赖关系明确 |
| L2 医疗标准映射、值域转换 | 是，规则由治理注册库生成或引用 | dbt 执行确定性转换；标准版本仍由治理模块拥有 |
| L3 主题模型、L4 指标宽表 | 是 | `ref()` 依赖、增量构建、测试和文档适合分析工程 |
| 构建期唯一性、非空、枚举、引用完整性检查 | 是 | 作为发布门禁，失败阻止模型晋级 |
| 面向业务人员的持续质量监控与问题闭环 | 否 | 使用 OpenMetadata/平台质量模块，dbt 结果作为输入 |
| CDC 搬运、亚秒级流式转换 | 否 | 使用 SeaTunnel、Doris 实时能力；dbt 负责批量或微批模型 |
| 资产目录、术语、审批、责任人、SLA | 否 | 使用 OpenMetadata 与平台治理流程 |
| MPI、黄金记录、合并拆分 | 否 | 使用 HAPI FHIR MDM 与平台主数据模块 |

质量规则采用“双入口、单身份”：开发人员在 dbt 中维护与模型构建强相关的门禁规则；治理人员在门户维护持续监控规则。每条规则拥有全局 `quality_rule_id` 和唯一执行模式，dbt 的 `run_results.json` 汇入 OpenMetadata，禁止在两个入口重复维护同一规则。

### 6.3 dbt 生产运行方式

1. 标准或映射发布后，治理模块生成/更新受控的 dbt 模型配置并形成 Git 变更。
2. 合并前运行 `compile + unit/data tests`，只构建受影响模型及下游。
3. DolphinScheduler 触发固定版本的 dbt 容器执行 `dbt build`，不在门户进程中直接运行 CLI。
4. `manifest.json`、`catalog.json`、`run_results.json` 和日志写入对象存储，作为本次发布证据。
5. OpenMetadata 摄取 dbt 制品，合并模型血缘、字段说明、标签和测试结果；平台再将状态呈现到治理界面。
6. 生产只允许发布不可变的项目版本；失败回退上一 Git tag/镜像并按原始证据重建目标模型。

首个兼容性基线建议从 `dbt-core 1.9.x + dbt-doris >=0.4` 开始，而不是直接追随最新主版本。进入 MVP 前必须通过 Doris `view/table/incremental`、迟到数据、删除/撤销、全量重建、失败原子性、中文字段、DECIMAL/DATETIME、dbt 制品进入 OpenMetadata 等验证。dbt-doris 官方文档未把 snapshot、model contract 等 dbt 通用能力列入适配器保证范围，因此不能在验证前将它们写入项目验收承诺。

## 7. 前置机设计

### 7.1 两种接入拓扑

1. **中心直连**：单院网络允许时，由中心 SeaTunnel 连接业务库，前置机只做网络边界或协议代理。
2. **站点采集**：区域/隔离网络下，在每院安装 Edge Node，由其读取本地系统并通过出站连接推送中心。

### 7.2 Edge Node 必须具备

- Windows 服务和 Linux systemd 两种离线安装包。
- 站点注册、能力清单、心跳、磁盘、版本、队列、最后成功位点和日志上报。
- 仅出站连接；中心不要求主动进入医院内网。
- 本地持久队列，容量按 72 小时峰值数据量配置。
- 配置版本、灰度发布、回退到上一版本和诊断包导出。
- 中心确认原始证据持久化后才清理本地内容。
- 断网期间继续采集或明确背压；恢复后补传速度至少为日常产生速度的 2 倍。

### 7.3 投递语义与幂等

不要对所有异构系统承诺绝对 exactly-once。采用“至少一次投递 + 中心幂等 + 可核对偏移量”：

- HL7 v2：`tenant + source + MSH-10 + message_type`。
- 数据库：`tenant + table + primary_key + change_version`。
- 文件：`tenant + normalized_path + size + checksum`。
- DICOM：`tenant + SOPInstanceUID + checksum`。

只有源系统提供稳定主键/消息 ID/日志位点、目标支持事务或幂等写入，并通过断网重放测试后，才可以在具体模板上声明无重复结果。

## 8. MPI、主数据与医疗标准

### 8.1 MPI 不是一次去重任务

患者/居民主索引必须包含：

- 字段标准化：姓名、证件、出生日期、电话、地址、曾用名和缺失值处理。
- Blocking：用证件、生日、电话、姓名组合缩小候选集合。
- 确定性和模糊匹配：生成 MATCH、POSSIBLE_MATCH、NO_MATCH。
- Crosswalk：所有源系统患者 ID 永久保留。
- 黄金记录和 survivorship：每个字段保留选值、来源和规则版本。
- 人工复核：对比证据、确认、拒绝、合并、拆分、撤销和影响预览。
- 可逆历史：规则版本、分数、操作者、时间和下游发布版本完整记录。

首期使用 HAPI FHIR MDM 的规则/相似度能力与平台审核流程。Splink 只做离线阈值评估和候选发现。由于 Soundex/Metaphone 等算法偏向西文，中文姓名、简繁体、同音字、新生儿、急诊未知患者、证件录入错误和手机号复用必须使用脱敏标注集单独验收。

错误合并的临床风险高于漏合并，因此默认策略应偏保守：高置信规则才能自动关联，中间区间进入人工复核，未经过标注集评估的概率结果不得自动改写黄金记录。

### 8.2 通用主数据域

- 机构、院区、科室、床位与位置。
- 医生、护士、人员、执业角色和任职关系。
- 疾病、手术、检验、药品、耗材、单位和值域。
- 数据源、接口、数据集、业务术语、指标和口径。

FHIR R4 用于表达 `Organization`、`Location`、`Practitioner`、`PractitionerRole`、`CodeSystem`、`ValueSet`、`ConceptMap`。审批、版本发布、差异比较、机构接收回执和撤回由平台主数据服务负责。

### 8.3 标准优先级

- 国内项目先覆盖实际验收所需的 WS/T 数据集、值域、共享文档和院内厂商字典。
- HL7 v2 继续作为院内实时接口主力，保留厂商 Z 段和原始消息。
- 对外服务与中心规范首期固定 FHIR R4，并通过项目 profile/extension 管理本地差异。
- CDA/共享文档与 FHIR 并存，不能因引入 FHIR 删除既有文档标准。
- DICOM 首期只采 Study/Series/Instance 元数据和 PACS/VNA 引用。
- OMOP CDM 只在科研、跨机构观察性分析项目中生成专题模型。

## 9. 统一门户与甲方获得感

### 9.1 用户与工作台

- 专业工作台：实施工程师、数据工程师、平台运维。
- 业务工作台：数据管理员、医务/病案/信息科、机关业务人员。
- 管理驾驶舱：院领导、信息中心负责人、区域管理者。
- 交付工作台：项目经理、甲方负责人、验收人员。

它们共享同一对象与数据，只改变首页、默认菜单、字段解释和可执行操作。

### 9.2 一级导航

1. 首页
2. 数据接入
3. 数据资产
4. 数据治理
5. 主索引与主数据
6. 数据服务
7. 分析看板
8. 智能问数
9. 运营中心
10. 交付中心

平台设置和引擎诊断放入管理菜单，仅专业用户可见。

“数据治理”不是跳转到 OpenMetadata 原生后台的单一菜单，而是一组面向甲方日常工作的一级产品页面。OpenMetadata 作为元数据、血缘、质量和术语的能力底座，通过 API 和嵌入式视图提供能力；门户统一中文业务语言、操作流程、权限入口和视觉风格。

### 9.3 数据治理工作台

数据治理采用“看成效—定标准—做映射—查质量—追影响—闭问题—控变更”的页面闭环：

| 页面 | 主要用户 | 核心呈现 | 关键操作与验收 |
|---|---|---|---|
| 治理驾驶舱 | 院领导、信息中心负责人、治理负责人 | 资产覆盖率、标准映射率、规则覆盖率、质量得分、问题闭环率、责任人覆盖率；按机构/系统/主题域下钻 | 任一红色指标两次点击内定位到责任对象、责任人和待办；指标显示口径、目标和趋势 |
| 数据标准 | 数据管理员、业务专家 | 业务术语、字段标准、值域、代码集、指标口径、标准版本和引用范围 | 支持检索、对比、评审、发布、停用；发布前展示受影响的数据集和接口 |
| 标准映射 | 数据治理人员、实施工程师 | 源字段到标准字段的映射矩阵、转换规则、覆盖状态、未映射清单和验证样例 | 批量导入/复用模板、人工修订、样例验证、提交评审；清楚区分未映射、待确认、已生效 |
| 数据质量 | 数据治理人员、数据工程师 | 完整性、唯一性、有效性、一致性、及时性规则；得分趋势、失败样例、执行历史 | 从数据集创建规则，失败自动生成问题单；修复后可重检并保留前后证据 |
| 血缘与影响 | 技术人员、数据管理员 | 从源系统、前置节点、任务、分层表到 API/报表的端到端血缘，支持表级和字段级视图 | 搜索对象、展开上下游、按环境/版本过滤；字段或任务变更前生成影响清单 |
| 问题闭环 | 治理负责人、责任部门、技术人员 | 问题等级、影响范围、责任人、SLA、根因、整改证据和状态轨迹 | 指派、接单、处理、复检、关闭和退回形成完整时间线；逾期自动进入治理驾驶舱 |
| 数据合同与变更 | 数据提供方、消费方、治理人员 | Schema、质量门槛、时效 SLA、负责人、版本差异和消费方 | 合同评审发布；破坏性变更自动拦截或要求审批，并通知受影响的报表/API 负责人 |

治理驾驶舱默认布局如下：

1. 顶部统一范围栏：机构、院区、系统、主题域、统计周期和“截至时间”。
2. 第一屏为六张结果卡，每张卡同时显示现值、目标、环比、责任人和下钻入口。
3. 中部左侧显示质量与标准覆盖趋势，右侧显示高风险系统/主题域排名。
4. 底部显示待办问题、逾期责任部门、近期标准变更和影响中的数据服务。
5. 页面只展示能解释、能下钻、能行动的数据，不放轮播、地球、粒子动画等装饰性大屏元素。

三类角色使用同一治理对象，但首页不同：管理者默认看到成效与风险，治理人员默认看到待评审、待映射和待闭环事项，技术人员默认看到规则失败、Schema 变更和血缘影响。任何治理指标都必须能回到具体数据集、规则、问题单和责任人，避免“有大屏、无抓手”。

### 9.4 必做页面与任务验收

| 页面 | 必须回答的问题 | 用户任务验收 |
|---|---|---|
| 接入向导 | 接什么、怎么取、何时到、写到哪、如何验收 | 标准数据库首表 30 分钟内完成接入，不登录服务器、不写 YAML |
| 任务详情 | 是否健康、数据多少、延迟多久、失败在哪、如何恢复 | 90% 日常操作在门户完成，可重试、补数、暂停、回滚 |
| 前置节点 | 在线吗、积压多少、会不会丢、何时追平 | 5 分钟内定位到节点、任务和错误建议 |
| 数据资产 | 是什么、从哪来、是否可信、谁负责、谁在用 | 业务人员 1 分钟内找到并判断目标数据集 |
| 治理驾驶舱 | 治理做得怎样、风险在哪里、谁在负责 | 两次点击内从异常指标定位到责任对象、责任人和待办 |
| 数据标准与映射 | 用什么标准、哪些已映射、变更影响什么 | 标准可评审发布，映射可验证复用，影响范围可预览 |
| 质量中心 | 哪条规则失败、影响什么、谁处理、何时关闭 | 失败自动转问题单，形成责任人与 SLA 闭环 |
| 血缘与影响 | 数据从哪来、流向哪里、改动会影响谁 | 表级/字段级下钻，变更前可导出影响对象和责任人 |
| 问题闭环 | 谁在处理、是否逾期、修复是否有效 | 指派、整改、复检、关闭全流程留痕，支持退回 |
| 数据合同与变更 | 提供什么、何时到、质量门槛是什么、能否变更 | Schema/SLA/质量规则版本化，破坏性变更需审批 |
| 主索引工作台 | 为什么像同一个人、选了哪个值、合错如何撤销 | 业务人员 3 分钟内处理一条候选，可预览影响并撤销 |
| 主数据发布 | 改了什么、谁审核、发给谁、是否接收 | 任一版本可比较、发布、回执、撤回 |
| 运营中心 | 哪个机构/系统风险最高、影响哪个服务 | 告警下钻到源、任务、表、规则和消费端 |
| 交付中心 | 做了多少、是否达到合同、证据在哪里 | 一键导出周报、月报和连续运行验收证据包 |

首轮高保真原型规划由原来的 7 个关键页面扩为 13 个：保留管理驾驶舱、接入向导、任务详情、前置节点、数据资产详情、质量中心和主索引复核；新增治理驾驶舱、数据标准、标准映射、血缘与影响、问题闭环、数据合同与变更。当前实际完成 9 个路由页面：管理驾驶舱、治理驾驶舱、数据标准、标准映射、质量闭环、主索引审核、数据资产、分析看板和智能问数，其中数据资产页合并覆盖“资产详情”和“血缘与影响”两个页面域。接入向导、任务详情、前置节点、问题闭环、数据合同与变更顺延到下一轮。标准中心的“列表—详情—版本对比”仍作为同一页面的三种状态，不拆成更多路由。

### 9.5 首页六个核心指标

- 接入覆盖率。
- 数据准时率。
- 加权数据质量得分。
- 主索引成效：黄金记录、候选、重复率变化。
- 数据服务成效：API/报表数量、调用量、活跃部门。
- 问题闭环率。

每个指标必须显示统计范围、截至时间、计算口径、目标值、趋势、责任人和下钻入口。所谓“获得感”来自自动产生的前后对比，而不是装饰性大屏，例如接入系统覆盖、人工导数工时下降、需求交付周期缩短、质量问题关闭量、MPI 重复率变化和数据服务使用量。

## 10. 轻量部署与运维产品化

轻量运维的关键不是把 Kubernetes 换成若干手工脚本，而是把交付和日常操作做成产品能力：

- 一份经兼容性测试的 BOM，固定每个组件版本和配置组合。
- 一个 `platformctl`：环境预检、安装、状态、备份、恢复、升级、回滚、诊断包。
- 一套 Compose 开发/PoC 包和一套 Helm 生产包，配置语义一致。
- 离线镜像仓库、离线安装包、校验清单和容量计算器。
- PostgreSQL 多 schema、共享对象存储和统一日志，减少重复基础设施。
- 组件失败原因转换成中文“原因—影响—建议”，不让甲方阅读 JVM/Pod 原始错误。
- 原生控制台只作为高级诊断后门，普通运维不依赖它们。

### 10.1 部署档位

| 档位 | 适用 | 形态 | 说明 |
|---|---|---|---|
| PoC | 1 院、10—20 表、验证链路 | 单台 Linux + Compose；前置机单独 Agent | 不承诺 HA；可裁剪 OpenMetadata/OpenSearch 等非关键能力 |
| 单院生产 | 10—20 系统、100—300 表 | 单节点 K3s + 外部备份，或 3 控制节点 K3s | 有 HA 合同要求时直接三节点，不能用两节点伪 HA |
| 区域试点 | 5—20 家医院 | 3 控制节点 + 可扩展 worker；每院 Edge Node | 机构级隔离、模板复用、中心不可用时站点缓存 |
| 区域规模化 | 多区域/大容量 | 现有 K8s 或独立集群；Doris/对象存储独立扩容 | 启用 Iceberg 能力包和跨机构数据产品治理 |

PoC 基线可按核心 8 vCPU/32 GB、完整治理演示 16 vCPU/64 GB 估算；这只是起步环境，不替代按源表数量、日增量、峰值吞吐、保留周期和查询并发做容量评估。标准 MiNiFi 前置节点可从 2 vCPU/4 GB 起步，启用 JVM CDC/医疗接口引擎时从 4 vCPU/8 GB 起步，本地磁盘按 72 小时峰值量计算。

### 10.2 安全与合规

第 2.2 节明确 PoC 暂不做完整等保、密钥托管和细粒度授权，但安全能力必须随部署档位同步补齐，不能在生产化阶段返工。以下机制全部建立在既有决策之上：单向数据流、事实归属、至少一次幂等，以及 `tenant_id`、机构隔离、操作审计从第一天保留。

**L0 证据层 PHI 加密与密钥管理**

- L0 原始证据包含完整 PHI，S3 兼容对象存储必须启用服务端加密（SSE），存储桶按租户和环境隔离，默认拒绝匿名访问和跨租户读写。
- 加密密钥由独立密钥管理服务托管：PoC 可使用对象存储自带 KMS，生产必须接入甲方认可的 KMS 或密评合规方案；密钥按合规要求定期轮换，轮换只更换包装密钥、重写密钥元数据，不重写存量证据对象，不破坏 `raw_object_uri + checksum` 的追溯关系。
- 密钥的创建、启用、轮换和销毁动作全部记录到审计日志；任何组件不得以明文形式把密钥写入配置文件、镜像或诊断包，`platformctl` 导出的诊断包必须先剔除密钥与凭据材料。
- 传输与边缘侧同样加密：采集链路和门户访问全程 TLS，前置机与中心之间使用双向认证的出站通道，断网缓存期间本地队列加密落盘，与第 7.2 节 Edge Node 能力要求衔接。
- 与第 2.2 节"暂不做密钥托管"的衔接：PoC 阶段先固定密钥来源和轮换接口，进入单院生产化前完成托管切换，并做一次轮换演练作为退出条件。

**去标识化与脱敏**

- 展示层脱敏：门户对证件号、电话、住址等直接标识符按角色默认脱敏显示；完整值只在有明确授权的审核场景（如 MPI 人工复核）中可见，且明文查看动作计入审计。
- 导出脱敏分级：导出物和数据产品分三级——原始级（仅限授权场景）、脱敏级（直接标识符不可逆替换）、去标识化级（准标识符泛化/抑制，供科研与区域共享）。分级标签随数据集登记到 OpenMetadata 资产元数据，导出统一由数据服务执行，不允许绕过平台从前端直接导出明文。
- MPI 阈值评估与验收一律使用脱敏标注集（见第 8.1 节），标注流程不产生新的明文副本。
- 脱敏规则本身版本化管理，与数据标准走同一评审发布流程；脱敏前后的映射关系不作为平台数据留存，避免形成可逆推回明文的索引。
- 非生产环境（开发、PoC、演示）一律使用脱敏或合成样本，生产 PHI 不进入非生产环境。

**细粒度授权模型**

- 采用 RBAC：角色绑定第 9.1 节的四类工作台，权限落到业务对象（数据集、规则、工单、主数据、数据产品）和操作（查看、编辑、发布、导出），不向甲方暴露组件级账号。
- 机构/租户隔离复用第一天保留的 `tenant_id` 与 `institution_id`：控制库查询、门户 API、Doris 行级策略和数据服务出口统一强制租户过滤；区域场景下机构用户只能看到本机构数据和区域级发布物，与"单院与区域同一代码路径"一致。
- 高敏操作（标准发布、MPI 合并/拆分、脱敏级导出、破坏性变更审批）要求二次确认并全程留痕，与第 13.4 节可逆变更模型一致。
- 最小权限为默认：授权变更（角色授予、回收、权限提升）统一由平台发起并记录，角色清单随版本评审；区域场景下跨机构授权需要双人复核。

**访问审计**

- 操作审计从第一天保留（第 2.2 节），审计事实归属 PostgreSQL 平台控制库：登录、查询、导出、发布、授权变更和 PHI 明文查看统一记录操作者、时间、对象、来源和结果。
- 审计日志只追加、不可修改，与证据层一样纳入备份、保留周期和容量计算；等保测评所需的留存周期在各部署档位的基线配置中固化。
- 审计查询入口放入运营中心，治理负责人可按操作者、对象和时间回溯；审计数据本身不向普通业务用户开放。

**等保补齐时间点**

- PoC：不做完整等保测评，但加密、租户过滤和审计字段不得缺省，避免形成无法迁移的存量数据。
- MVP：完成安全基线自查（口令策略、传输加密、最小化开放端口与组件账号收敛），不要求正式测评，但输出机器生成的检查记录并纳入交付证据包。
- 单院生产化（第 11 节）：上线前完成等保二级定级、备案与测评；密钥托管切换、审计留存和备份恢复演练纳入该阶段退出条件。
- 区域试点（第 11 节）：跨机构共享前完成等保三级测评；机构间隔离有效性、导出脱敏分级和区域级审计与"新院首批数据 1 个工作日内可见"并列，作为该阶段强制退出条件。

## 11. 交付路线

周期按 4—6 人小团队估算；若只有 3 人，完整 MVP 不应承诺同样周期。

| 阶段 | 周期 | 可交付范围 | 退出条件 |
|---|---:|---|---|
| P0 需求与验证 | 2 周 | 源系统清单、网络/权限验证、数据样本、交互原型、组件兼容性 spike | 至少验证 1 个数据库、1 个前置协议、1 条端到端数据链 |
| PoC 垂直切片 | 4—6 周 | 1 院、1 前置节点、3 类源、10—20 表、批量+一种增量、10 条质量规则、确定性 MPI、门户首页 | 60 分钟内安装；30 分钟首表；连续 7 天成功率达到约定值；断网 24 小时重放通过 |
| MVP | 再 8—12 周 | 5—8 个源、50—100 表、模板、资产目录、血缘、质量闭环、MPI/MDM、运营/交付中心、嵌入 BI | 90% 标准运维在门户完成；连续 14 天 SLA；标注集 MPI 验收；备份恢复演练通过 |
| 单院生产化 | 再 6—10 周 | 10—20 系统、正式主数据发布、数据服务、离线包、性能、培训和移交 | 连续 30 天 SLA；2 倍峰值压测；72 小时缓存；RTO 达成；证据包可导出 |
| 区域试点 | 再 12—20 周 | 5—20 院、多机构模板、区域 EMPI、机构隔离、区域驾驶舱 | 新院首批数据 1 个工作日内可见；模板复用率 ≥80%；单院故障不影响其他机构 |

## 12. 验证与验收清单

### 12.1 正常路径

- 数据库全量后切换增量/CDC，记录数和主键范围可核对。
- 文件重复上传、断点续传和校验和去重。
- HL7 正常 ACK、消息追踪和原文回看。
- L0→L4 每层能定位数据、任务和转换版本。
- 质量规则失败生成工单，修复后重跑并关闭。
- MPI 确定匹配、可能匹配、拒绝、合并、拆分和撤销全流程。
- Superset 图表、数据 API 和文件产品均能追到指标口径和源数据集。

### 12.2 故障路径

- 中心断网 24/72 小时、前置节点重启、磁盘接近阈值、中心恢复补传。
- SeaTunnel worker/任务失败后从检查点恢复。
- 源 schema 增列、删列、类型变化和主键变化；发布前展示影响面。
- 对象存储、OpenMetadata、Superset 分别不可用时的降级边界。
- 重复消息、乱序变更、延迟到达和删除事件。
- 组件升级失败后的 Helm/应用版本回滚，以及数据定义回到上一发布版本。

### 12.3 边界路径

- 无证件新生儿、急诊未知患者、外籍人员、双胞胎、曾用名、手机号复用。
- 中文姓名简繁体、同音字、录入错别字和证件历史错误。
- 超大表首次全量、无主键表、源库不开放日志权限。
- 同一机构多个院区、同名科室、人员跨机构执业。
- 区域 EMPI 拆分后，下游数据产品仍能解释历史版本。

### 12.4 建议合同指标

- 标准源首表接入中位时长 ≤30 分钟。
- 标准日常运维操作 ≥90% 在统一门户完成。
- 失败/延迟 5 分钟内可见，并下钻到责任对象。
- 前置节点缓存 72 小时，恢复后清积压速度 ≥日常产生速度 2 倍。
- 按合同实际峰值 2 倍完成压测。
- MPI 在双方共同标注的脱敏样本上分别验收自动匹配 precision、候选 recall 和人工复核效率；自动合并阈值应优先控制误合并。
- 5 名技术用户和 3 名业务用户完成任务测试，任务成功率 ≥90%。
- 安装、备份、恢复和升级回滚均提供机器生成的验收记录。

## 13. 关键风险与应对

### 13.1 最脆弱假设

本方案最依赖的假设是：80% 以上医院接入可由 JDBC、文件、HTTP/SFTP、HL7 v2/MLLP 和标准模板覆盖。如果厂商不开放数据库/CDC、只提供私有 WebService/SDK，交付速度会由“平台能力”转为“逐接口开发”。

应对方式是把 P0 的源系统与权限核查设为合同前置条件，准备 Camel 插件 SDK 和文件/API 兜底，但只向专业用户开放，不能破坏业务门户的一致体验。

### 13.2 依赖失败

- 前置节点失去中心连接：继续本地缓存，按磁盘阈值告警；不静默丢弃。
- OpenMetadata 不可用：采集和数仓继续运行，元数据事件暂存后补录。
- Superset 不可用：只影响分析展示，不阻塞采集、治理和 MPI。
- 对象存储不可用：采集端背压，不能绕过 L0 原始证据直接发布标准结果。
- HAPI FHIR/MPI 不可用：原始和标准数据继续进入待匹配区，不创建不可追溯的临时区域身份。

### 13.3 10 倍规模

首先承压的通常不是门户，而是前置磁盘、同步 worker、Doris 存储/compaction、元数据索引和调度并发。架构通过 Edge Node 分散缓存、SeaTunnel worker 横向扩展、Doris BE 扩容、元数据异步采集来承受增长；达到开放湖仓决策门槛后，将冷数据迁移到 Iceberg 而不是继续无限扩大热仓。

### 13.4 回滚成本

- 应用和组件：固定 BOM + Helm revision 回滚。
- 接入/转换/质量：每次发布生成不可变版本，可切回上一版本。
- 数据：原始证据不变；标准/主题表通过新表重算和别名切换，避免原地不可逆修改。
- MPI/MDM：合并、拆分、survivorship 和发布均以事件记录，支持撤销与重放。
- 数据库迁移：只允许向前兼容的扩展性迁移；需要破坏性迁移时先双写/回填再切换。

## 14. 备选方案

### 14.1 最小 PoC

若目标只是 6 周内证明价值，可先部署：统一门户、PostgreSQL、SeaTunnel、Doris、dbt Core 转换容器、Superset、一个前置执行器和 HAPI FHIR MDM。资产目录先使用平台自身最小元数据，OpenMetadata、完整调度、Iceberg 和区域扩展在 MVP 加入。

优点是最快形成“接入—质量—MPI—看板”闭环；代价是 PoC 的资产/血缘和跨任务编排不是最终形态，进入 MVP 时需要按已确定的适配器接口接入 OpenMetadata/DolphinScheduler。

### 14.2 从第一天建设纯开放湖仓

替代方案是对象存储 + Iceberg v2 + PostgreSQL JDBC Catalog + Trino + SeaTunnel。SeaTunnel 负责 CDC/upsert 写入，Trino 负责查询以及 `OPTIMIZE`、快照过期和孤儿文件清理；达到区域化或多引擎规模后，再把 JDBC Catalog 升级为 REST Catalog。该方案不强制依赖 Spark/Flink，更接近 Databricks 的开放湖仓形态，适合已有湖仓团队、科研/AI 是首要负载、数据规模已达到数十 TB 且多引擎开放是合同要求的项目。

不推荐小团队默认采用，因为首期会同时承担 catalog、对象存储、计算引擎、小文件/compaction、CDC delete/upsert、查询加速和运维门户的复杂度。

## 15. 待确认的架构决策

这些不是设计空白，而是进入实现前由明确责任人完成的决策门：

| 决策 | 当前建议 | 决策责任人/时间 | 若结论相反 |
|---|---|---|---|
| 首期热仓还是纯湖仓 | Doris 热仓 + 对象证据层 | 产品/技术负责人批准本蓝图时 | 改用 14.2，周期和运维投入重新估算 |
| 首个前置执行器 | 按首院样本在 MiNiFi 与 OIE 中二选一 | 实施负责人在 P0 第 1 周 | 若两类协议都占主流，形成两个站点能力包而非同机默认叠装 |
| HAPI FHIR MDM 适用度 | 用于规则匹配和 FHIR 表达，平台补流程 | 数据治理负责人在 P0 第 2 周用脱敏样本验证 | 保留平台 crosswalk/流程，替换匹配引擎 |
| SeaTunnel 门户适配 API | 优先稳定版 REST V2/CLI 能力 | 平台负责人在 P0 第 1 周做版本兼容 spike | 通过 CLI/事件监听适配，不暴露引擎差异 |
| dbt-doris 生产基线 | PoC 从 dbt-core 1.9.x + dbt-doris ≥0.4 验证，BOM 固定实际通过版本 | 数据平台负责人在 P0 第 2 周 | 若增量、制品或类型兼容不达标，保留转换模块接口并改用受控 Doris SQL 任务 |
| 对象存储实现 | 保持 S3 接口可替换 | 交付与法务在首个商用项目立项时 | 换用甲方现有 S3、云对象存储或许可证合适的自托管实现 |
| 前置机 OS | 同时支持 Windows 服务与 Linux systemd | 售前/实施在首院资源核查时 | 只交付已验证 OS 包，不把容器运行时强加给甲方 |

## 17. 已批准设计摘要（批准后生效）

- **建设内容**：统一医疗数据门户、采集与前置节点、分层数据、资产治理、质量闭环、MPI/MDM、数据服务、嵌入式分析、运营和交付中心。
- **不建设内容**：首期不做全套 AI/ML、PACS/VNA 替代、DICOM 像素湖、通用大数据组件集群和无边界的低代码开发平台；NiFi 服务端不作为默认编排/采集组件（2026-07 data-ops 实验结论，见第 5.1 节决策记录）。
- **实施路线**：Doris 热仓 + 对象证据层起步，SeaTunnel 为数据库同步主引擎，前置执行器按协议选择，HAPI FHIR MDM 为医疗身份底座，OpenMetadata/Superset 通过统一门户交付。
- **关键决定**：不暴露组件拼盘；单院与区域共用租户模型；至少一次 + 幂等；MPI 全程可逆；生产交付工具与业务功能同等优先。
- **明确延期项**：Iceberg/Trino、Splink 在线化、OMOP、Snowstorm、完整 DICOM 归档和 AI/ML，只在相应业务门槛出现后启用，由产品与技术负责人按第 15 节决策门评审。
